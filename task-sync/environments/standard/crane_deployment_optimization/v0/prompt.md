You are the shift planner at a large container terminal. Your job for the current shift is to produce a prioritized crane worklist that tells each yard crane operator exactly which container to handle next, in what order, so that vessel turnaround time is minimized. The shift timing, including its start and end, is recorded in `shift_config.json`. All scheduling decisions should be made relative to this window.

Begin by reading the terminal's configuration files. `terminal_layout.json` describes which yard blocks belong to which zone and which berths sit inside each zone. `crane_specs.yaml` lists every yard crane, its home zone, and its maximum lifting capacity in tons. `priority_rules.yaml` contains the scoring model you must follow, the crane-selection policy, the maintenance buffer rule, and the estimated handling durations for twenty-foot and forty-foot containers. `maintenance_schedule.yaml` holds additional scheduled maintenance windows that may not yet appear in the gate system. `operational_policy.md` provides supplementary handling guidelines.

Identify every vessel currently berthed by querying the vessel registry. For each berthed vessel, retrieve its departure deadline. Then collect all containers associated with those vessels whose status is either pending discharge or pending load; these are the items that need crane operations during this shift.

Some containers may lack a recorded yard-block position in the registry. For those, consult the GPS position log files, which are CSV files whose names start with `gps_position_log_`. Each row contains a timestamp, a container identifier, coordinates, and a detected block. Use the most recent reading per container to determine its current yard block.

Discharge and load sequences come from the stowage-plan files, one JSON file per berthed vessel, named after the vessel identifier. Each plan has a discharge section and a load section listing every container with its sequence number. The sequence number is critical for scoring: a container at sequence one should be handled before one at sequence fifteen.

Compute an urgency score for every container in the worklist. The score is the sum of several components. First, a deadline component: compare the hours remaining until the vessel departs against the tier thresholds in the priority rules; the container receives the score of the first tier whose maximum-hours value is greater than or equal to the remaining hours, or zero if none applies. Second, a truck-waiting component: if an active truck is associated with this container, add the truck waiting bonus. A truck counts as active if the gate system lists it with a status of waiting or processing. Separately, check the truck manifest batch files (CSV files whose names begin with `truck_manifest_batch_`). If a manifest entry for the container has a scheduled arrival within the shift window and the container is not already marked as completed in the gate system, the truck bonus also applies. Third, if the container is flagged as hazardous material, add the hazmat bonus. Fourth, if it is a reefer container, add the reefer bonus. Fifth, compute the sequence component as the sequence weight minus the quantity (sequence number minus one), floored at zero. All component values are defined in the priority rules file.

Sort the resulting list in descending order of urgency score. When two containers share the same score, the one whose vessel departs sooner comes first. If deadlines also match, sort by container identifier in ascending alphabetical order.

Assign a crane to each container using the greedy method described in the priority rules. Process containers in the sorted order above. For each container, determine its zone from the terminal layout using the container's yard block. Among the cranes in that zone, exclude any crane whose lifting capacity is below the container's weight, and exclude any crane that is unavailable due to maintenance. A crane is unavailable if any maintenance window, after subtracting the maintenance buffer from the start time, overlaps with the shift period; check both the gate-system maintenance logs retrieved per crane and the workspace maintenance schedule. From the remaining candidates, pick the crane that currently has the fewest assignments in the worklist being built; if there is still a tie, choose the crane whose identifier comes first alphabetically. If no crane qualifies, record the crane identifier as NONE.

For each entry, determine the estimated duration in minutes from the duration estimates in the priority rules, choosing the value that matches the container's size.

Save the final worklist as `crane_worklist.csv` with the following columns in this exact order: `priority_rank`, `crane_id`, `container_id`, `vessel_id`, `vessel_name`, `operation_type`, `yard_block`, `estimated_duration_min`, `urgency_score`. The priority rank is a sequential integer starting at one. The operation type is `discharge` for pending-discharge containers and `load` for pending-load containers. Every value should appear exactly as described, with no extra whitespace or quoting beyond standard CSV conventions.

Separately, save a summary as `summary_report.json` containing these fields: `total_operations` (integer count of worklist rows), `vessels_served` (a sorted list of unique vessel names in the worklist), `cranes_deployed` (integer count of unique crane identifiers actually assigned, excluding NONE), `average_urgency_score` (the mean urgency score across all entries, rounded to two decimal places), `critical_operations` (integer count of entries whose urgency score is seventy or above), and `estimated_total_hours` (the sum of all estimated durations converted to hours, rounded to two decimal places).

In your final response, state the total number of crane operations scheduled, the number of vessels served, the number of unique cranes deployed, and the count of critical operations.
