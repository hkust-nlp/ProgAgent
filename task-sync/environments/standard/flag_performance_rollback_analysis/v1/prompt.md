You are responsible for reviewing the impact of recent feature flag configuration changes across the application platform. Your goal is to produce a comprehensive rollback recommendation report by correlating flag changes with application error logs, user session analytics, and support ticket volume. Multiple sources of information are available to you: structured data accessible through your analytical tools, as well as configuration files, session performance records, flag metadata, and incident documentation located in your working directory.

Begin by examining the rollback policy configuration, stored as a YAML file, to understand the analysis parameters. This file specifies the observation window size in days, the lookback period for identifying recently modified flags, a reference date anchoring the analysis, and the numeric threshold values that govern both rollback and monitoring decisions. A separate JSON configuration file provides the criticality classification for each service in the platform; you will need this to populate the criticality column in your report.

Using your tools, retrieve the complete list of feature flags and identify those whose most recent configuration change falls within the lookback period measured backward from the reference date. For every such flag, obtain a comparison of key metrics between the period before the change and the period after it, using the window size specified in the policy. The metrics you need from this comparison are error count, average user satisfaction score, session count, and support ticket count for both windows.

In addition to tool-derived metrics, you must compute the average response time change for each flag from session performance CSV files found in your directory. These files are organized in a subdirectory and contain per-session records with fields for exposed flag identifiers, response time measurements in milliseconds, and timestamps. For each recently changed flag, filter sessions where that flag appears among the exposed flags, split them into the before and after windows relative to the flag's most recent change date using the same window size from the policy, compute the average response time for each window, and express the change as a percentage relative to the before-window average, rounded to one decimal place.

Flag metadata JSON files in your directory provide each flag's rollback complexity classification and ownership information. Read all of these files and map each flag to its rollback complexity value, which should be included in the final report. Incident report text files should also be reviewed; each file may reference specific flags by name and numeric identifier. Determine whether each flag under analysis is mentioned in any incident documentation and record this as a yes or no indicator.

Once all metrics are gathered, apply the rollback policy thresholds to classify each flag. A flag receives a ROLLBACK recommendation if its error increase percentage exceeds the rollback error increase threshold, or if the magnitude of its satisfaction drop exceeds the rollback satisfaction drop threshold, or if the ratio of after-window ticket count to before-window ticket count exceeds the rollback ticket spike multiplier. A flag receives a MONITOR recommendation if any of these three metrics exceeds the corresponding monitor-level threshold but none reaches the rollback level. All other flags are classified as KEEP. When determining the primary reason for a recommendation, evaluate the metrics in the following order: error rate increase, satisfaction drop, and ticket volume spike. The primary reason is the first metric in this sequence whose value exceeds the relevant threshold. Use "error_increase" for error rate, "satisfaction_drop" for satisfaction, and "ticket_spike" for ticket volume. Flags classified as KEEP should have "within_limits" as the primary reason.

For the error increase percentage, compute it as the difference between after-window and before-window error counts divided by the before-window count, multiplied by one hundred, and rounded to one decimal place. If the before-window count is zero and the after-window count is positive, treat the percentage as the after-window count multiplied by one hundred. The satisfaction change is the after-window average satisfaction minus the before-window average, rounded to two decimal places, so a decline appears as a negative number. The ticket ratio is the after-window count divided by the before-window count, rounded to two decimal places; if the before-window count is zero, use the raw after-window count as the ratio.

Save the results as `rollback_report.csv` with the following columns in this exact order: `flag_id`, `flag_name`, `service`, `criticality`, `error_increase_pct`, `satisfaction_change`, `ticket_ratio`, `avg_response_time_change_pct`, `rollback_complexity`, `mentioned_in_incidents`, `recommendation`, `primary_reason`. Sort the report by recommendation priority with ROLLBACK rows first, then MONITOR, then KEEP, and within each group sort by `flag_id` in ascending order.

In your final response, state the total number of flags analyzed, how many received each recommendation type, and list the flag names recommended for rollback along with their services and primary reasons.
