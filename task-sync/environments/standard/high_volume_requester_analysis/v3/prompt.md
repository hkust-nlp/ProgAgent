You are assisting the legal compliance division of a municipal government that receives public-records requests from citizens, journalists, businesses, and other entities. Concerns have been raised that certain requestors may be systematically extracting large volumes of government data for commercial purposes, sometimes exploiting fee waiver provisions intended for public-interest disclosures. Your job is to analyze all available data, apply a structured risk-scoring methodology, and produce a report identifying requestors who warrant further legal review.

Begin by reading the configuration files that define the detection methodology. A YAML file specifies the volume threshold (the minimum number of filed requests that qualifies a requestor as high-volume), a composite risk-score threshold above which a requestor is flagged, a set of scoring weights for six risk components, and normalization caps for three of those components. A JSON file lists the email domains known to belong to commercial data brokers or bulk-records aggregators. A CSV file maps each department to a sensitivity level on a one-to-five scale. Another JSON file maps each request category to an integer risk score on a one-to-ten scale. A policy document in Markdown describes how fee waiver approval patterns should be interpreted and defines which waiver-reason phrases are considered commercially oriented.

Using the available search tools, retrieve all filed public-records requests and group them by requestor. Any requestor whose total number of requests equals or exceeds the volume threshold must be evaluated further. For every such high-volume requestor, gather their contact details, their aggregate document-production statistics, and their fee waiver records through the appropriate tools.

Compute a composite risk score for each high-volume requestor using six weighted components. The first component is request volume, calculated as the requestor's total request count divided by the volume normalization cap, capped at one. The second is a commercial domain match indicator, set to one if either the requestor's primary email domain or an alternate email domain found in the requestor profile files matches any domain on the known-commercial-domains list, and zero otherwise. The third is the fee waiver ratio, equal to the number of approved fee waivers for that requestor divided by their total number of requests. The fourth is department spread, calculated as the count of distinct departments targeted by the requestor's requests divided by the department-spread normalization cap, capped at one. The fifth is document sensitivity, derived from the production manifest files: for each of the requestor's requests that appears in a manifest, note the recorded average document sensitivity, then average those values across all matched requests and divide by five. If no manifest entries exist for the requestor's requests, this component is zero. The sixth is cross-agency history, taken from the requestor profile files: divide the requestor's cross-agency request count by the cross-agency normalization cap, capped at one. If the requestor has no profile record, treat both the alternate email and cross-agency count as absent (empty string and zero respectively).

Multiply each component by its corresponding weight from the configuration, sum the six products, and round the result to four decimal places. A requestor whose composite risk score meets or exceeds the risk-score threshold is flagged.

For every flagged requestor, assemble a set of flag reasons. Include "commercial_domain_match" when the commercial-domain indicator is one. Include "high_fee_waiver_ratio" when the fee waiver ratio exceeds fifty percent. Include "wide_department_spread" when the number of distinct departments targeted equals or exceeds the department-spread normalization cap. Include "high_cross_agency_activity" when the cross-agency request count equals or exceeds the cross-agency normalization cap. Separately, review the text of each approved fee waiver reason for that requestor; if any approved waiver reason contains the word "commercial", the phrase "market analysis", the phrase "bulk data", or the phrase "aggregation" (case-insensitive), add "commercial_waiver_language" to the reasons. Sort the reason labels alphabetically and join them with "; " as a delimiter.

Save the results as `flagged_requestors_report.csv`. The file must contain exactly these columns in this order: `requestor_id`, `requestor_name`, `email`, `organization`, `num_requests`, `risk_score`, `flag_reasons`, `total_pages_produced`, `approved_fee_waivers`, `departments_targeted`. Rows must be sorted by `risk_score` in descending order. The `risk_score` column must show four decimal places. The `total_pages_produced` column reflects the sum of all pages from the production summary for that requestor. The `approved_fee_waivers` column is the count of fee waivers with status "approved". The `departments_targeted` column is the count of distinct department IDs across the requestor's requests.

Once the report is saved, state in your final response how many requestors were flagged and list every flagged requestor ID in descending risk-score order.
