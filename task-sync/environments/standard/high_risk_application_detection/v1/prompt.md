You are tasked with producing a prioritized review queue of all pending loan applications for the underwriting team. Every application currently in "pending" status must be assessed and ranked by a composite risk score derived from six distinct factors, each drawing on a different data source.

The six risk components are: credit score risk, debt-to-income ratio risk, fraud severity risk, regional default risk, loan-to-value ratio risk, and prior default risk. A configuration file in YAML format specifies the weight assigned to each component, the threshold tiers that map raw values to risk factors between zero and one, and the boundaries for priority-tier classification. You will need to locate and read this file carefully, as every numeric parameter for the scoring formula is defined there.

For each pending application, retrieve its credit bureau report through the available tools. The report provides the applicant's credit score and monthly debt payment, among other fields. Map the credit score to the appropriate tier defined in the configuration to obtain the credit score risk factor. Separately, gather the applicant's verified annual income from the income verification batch files stored alongside the configuration. Compute the debt-to-income ratio by dividing the monthly debt payment from the credit report by the applicant's monthly income, which is the verified annual income divided by twelve. If no income record exists for an applicant, treat the ratio as one. Match the resulting ratio against the DTI threshold tiers in the configuration to determine the DTI risk factor.

For fraud severity, retrieve all fraud alerts associated with the applicant through the tools. Consider only alerts that have not been resolved. If there are unresolved alerts, look up each alert's severity in the fraud severity scores table from the configuration and take the maximum value as the fraud risk factor. If no unresolved alerts exist, the fraud risk factor is zero. For regional default risk, query the tool that returns the average default rate for the applicant's region over the most recent three years and map the returned percentage to the regional risk threshold tiers in the configuration. For loan-to-value ratio, divide the loan amount by the appraised value found in the property appraisal files for that application. Only mortgage and home equity loans have corresponding appraisal records; for all other loan types, use the default non-applicable risk factor provided in the configuration. Match the computed LTV against the LTV threshold tiers to get the risk factor. Finally, for prior default risk, retrieve the applicant's loan history through the tools, count the number of prior outcomes recorded as "defaulted," and match that count against the prior default risk tiers in the configuration.

The composite risk score is the sum of each component's weight multiplied by its risk factor. Once all base scores are computed, read the underwriting policy document included alongside the configuration. It describes a sequence of override rules that must be applied after the base calculation. The specific numeric thresholds for these overrides are defined in the policy overrides section of the configuration file. Apply each override rule in the order it is listed in the policy document. Overrides may adjust the computed score or force a minimum priority tier depending on conditions related to fraud alerts and debt-to-income ratios. After all overrides have been applied, assign each application a priority tier by checking tiers from the most urgent downward; the first tier whose minimum score threshold is met or exceeded by the application's final risk score determines its assignment.

Save the completed review queue as `review_queue.csv` with columns in this exact order: `application_id`, `applicant_name`, `risk_score`, `priority_tier`, `primary_risk_factor`, `loan_amount`, `region`. Sort rows by `risk_score` in descending order; where two applications share the same risk score, break the tie by `application_id` in ascending lexicographic order. Format each `risk_score` to exactly four decimal places and each `loan_amount` to exactly two decimal places. The `primary_risk_factor` column should contain the name of the risk component whose weighted contribution, meaning the product of its weight and its risk factor, is the largest in the base calculation before any override adjustments.

Separately, produce a file named `risk_summary.json` containing four keys: `total_applications_reviewed` holding the integer count of all pending applications you evaluated, `tier_counts` as an object mapping each priority tier name to the number of applications assigned to it, `tier_average_scores` as an object mapping each tier to the mean risk score of its applications rounded to four decimal places, and `highest_risk_application` holding the application ID of the single highest-risk entry.

In your final response, state the total number of pending applications reviewed, the count of applications in each priority tier ordered as critical then high then medium then low, and list the top three highest-risk applications with their application ID, applicant name, risk score, priority tier, and primary risk factor.
