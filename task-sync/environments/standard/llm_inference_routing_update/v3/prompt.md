You are the routing operations engineer for a large-scale LLM inference platform that serves dozens of models organized into four service tiers: economy, standard, premium, and enterprise. Your objective is to audit every active model for SLA compliance, compute cost-effectiveness scores, enforce prompt-length limits, and update the routing rules accordingly. A model is considered active if its status is anything other than "inactive"; models marked "degraded" are still subject to analysis.

Begin by examining the configuration and policy files that govern the platform's behavior. A YAML policy file specifies, for each tier, the maximum acceptable p95 latency in milliseconds, the maximum error rate, the maximum number of open incidents before a model should be flagged for review, a critical-incident threshold that determines when a model must be deactivated rather than merely demoted, and a promote-top-percentage value that identifies what fraction of well-performing models in each tier may be promoted. A JSON configuration file describes the cost-effectiveness formula, listing the weights for quality, satisfaction, and price, along with per-tier prompt-length thresholds in tokens and priority adjustment values for demotion, promotion, and deactivation actions. A CSV file provides a cost adjustment factor for each provider that must be multiplied into the pricing denominator when computing effective cost.

The platform also maintains several collections of data files that you must read in their entirety. CSV files capture latency-window snapshots, each recording per-model average latency, retry rate, and a client satisfaction score that is not available through any tool query. JSON files describe client request patterns, listing which models each client prefers and their cost sensitivity. Markdown files detail individual incidents by identifier, including a root cause category and an estimated financial impact in dollars, both of which are available only in these files. YAML files provide model quality benchmark scores that are likewise exclusive to the file-based data. You will need all of these supplementary values to compute cost-effectiveness and to assemble the violation report.

For every active model, retrieve its latency percentiles and check whether its p95 latency exceeds the tier-specific SLA threshold from the policy file. A model is SLA-compliant only when its p95 latency is at or below that threshold. Also gather each model's SLA violation incident history, noting how many incidents remain in an open status and how many of those open incidents carry a severity of critical or high.

Compute a cost-effectiveness score for each active model. The formula, described in the JSON configuration file, works as follows: the numerator is the sum of the model's quality score multiplied by the quality weight and its average client satisfaction score multiplied by the satisfaction weight; the denominator is the average of the model's input and output prices per million tokens, multiplied by the provider's cost adjustment factor, multiplied by the price weight. If a model has no quality benchmark entry, use 0.50 as the quality score. If no satisfaction data exists for it, use 0.50 as the average satisfaction. If the provider does not appear in the adjustment schedule, apply a factor of 1.00. Round the resulting cost-effectiveness score to four decimal places.

With SLA compliance, incident data, and cost-effectiveness in hand, determine a single routing action for each active model by evaluating the following conditions in strict order of precedence. First, if the model's p95 latency exceeds its tier threshold and the count of its open incidents with severity critical or high is greater than or equal to the tier's critical-incident threshold, the action is "deactivate" and the model's routing priority must be set to the deactivation priority value from the configuration while its active flag is set to zero. Second, if the model's p95 exceeds the threshold but the critical-or-high count falls below the critical-incident threshold, the action is "demote" and the priority increases by the configured demotion amount. Third, if a model is SLA-compliant but has strictly more total open incidents than the tier's maximum-open-incidents limit, the action is "flag_review" and its priority remains unchanged. Fourth, among the remaining SLA-compliant models in each tier, those whose cost-effectiveness score places them in the top percentage defined by the tier's promote-top-percentage are given the action "promote" and their priority decreases by the configured promotion amount, with a floor of one. When computing how many models to promote, multiply the count of remaining compliant unflagged models in that tier by the percentage, take the integer part, and ensure at least one is promoted if any candidates exist. All other models receive the action "maintain" with no priority change.

Separately, for every active model, compare its current routing rule's prompt-length limit against the tier-specific prompt-length threshold from the configuration. If they differ, update the prompt-length limit to the prescribed value regardless of which action category the model falls into.

After determining all actions, execute the necessary routing rule updates through the available update mechanism. Then save a file named `routing_decisions.csv` containing one row per active model with the columns `model_id`, `model_name`, `tier`, `p95_latency_ms`, `sla_compliant`, `cost_score`, `open_incidents`, `new_priority`, and `action`. Format the p95 latency to two decimal places and the cost score to four decimal places. Express SLA compliance as `yes` or `no` in lowercase. Sort the rows first by tier in alphabetical order, then by new priority in ascending numeric order, and break remaining ties by model ID in ascending order.

Also save a file named `violation_report.json` containing a JSON object with the following structure. The key `total_violations` holds the count of models whose p95 latency exceeded their tier's SLA threshold. The key `by_tier` maps each tier that has at least one violation to its violation count. The key `by_severity` maps each of the four severity levels to the total count of open incidents across all violating models at that severity. The key `top_violators` is a list of entries for every violating model, sorted by total impact dollars in descending order, where each entry contains `model_id`, `model_name`, `open_incident_count` giving the number of incidents with status open for that model, `total_impact_dollars` giving the sum of estimated financial impact across all of that model's incidents found in the detail files rounded to two decimal places, and `affected_client_count` giving the number of unique clients who list that model among their preferred models in the request pattern files. The key `overall_sla_compliance_rate` is a string formatted as a percentage with two decimal places followed by a percent sign, representing the share of active models that are SLA-compliant.

In your final response, state the total number of active models analyzed, the number of SLA-violating models found, the model ID and cost-effectiveness score of the most cost-effective model in each tier in the format "tier: model_id (score)", the total number of routing rule updates performed, and the counts of models assigned to each action category that has a nonzero count.
