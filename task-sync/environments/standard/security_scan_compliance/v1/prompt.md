Your organization enforces mandatory security scanning on all code changes before they reach production. Every pull request that gets merged must have undergone the correct set of CI pipeline scans, and any security findings of sufficient severity must have been reviewed by an authorized individual before the merge was finalized. Your job is to audit the entire history of merged pull requests, cross-reference their commit pipelines and scan results against the organization's compliance policies, and produce a prioritized remediation backlog of every violation discovered.

Begin by reading the scan policy configuration file, which is a YAML document named `scan_policy.yaml`. It defines three compliance tiers, each specifying which scan types are mandatory and which finding severity levels require pre-merge review. The file also contains a violation priority matrix that maps each type of violation and its associated severity or tier to a priority level ranging from P1 through P4. You will need these mappings throughout the analysis.

Separately, a CSV file named `authorized_reviewers.csv` lists every person in the organization who holds a security review certification. Each row provides the reviewer's name, the maximum severity level they are authorized to review, their certification expiry date, and their department. When checking whether a finding was reviewed by a qualified person, compare the finding's severity against the reviewer's maximum authorized severity: a reviewer authorized for "high" may review high, medium, and low findings, but not critical ones. A reviewer authorized for "critical" may review all severities.

There is also a JSON file called `sla_config.json` that defines the remediation SLA windows in hours for each severity level, a baseline date, and an escalation policy description per priority tier. This file is provided for context on how quickly each priority level should be addressed, but the SLA deadlines themselves do not factor into violation detection; they inform the remediation urgency once violations are identified.

The remaining files in your environment are a series of JSON documents whose names begin with `pr_metadata_` followed by a sequence number. Each of these files contains an array of objects, one per pull request, providing the pull request number, its compliance tier assignment, deployment target, whether branch protection was enabled, any labels attached, and linked issue tracker tickets. The compliance tier from these metadata files is the authoritative source for determining which scan policy applies to each pull request. Collect all of these entries to build a complete mapping from pull request number to compliance tier before proceeding.

Once you have the policy, reviewer authorizations, and per-PR tier assignments in hand, retrieve every merged pull request through the available listing interface. For each merged pull request, gather its associated commits, then for each commit retrieve the CI pipeline runs that executed against it. A scan counts as having been performed for a pull request if at least one pipeline run of that scan type across any of the pull request's commits completed with a status other than "skipped". Compare the set of scans actually performed against the set required by the pull request's compliance tier. Any required scan that was never run, or was only ever skipped, constitutes a "missing_required_scan" violation.

For every pipeline run that corresponds to a security scan type, retrieve the findings it produced. Focus on findings whose severity matches the pre-merge review requirement for the pull request's compliance tier. A finding with status "open" on a merged pull request is an "unreviewed_finding" violation. For findings that have been reviewed or dismissed, verify two things: first, that the person who performed the review is listed in the authorized reviewers file and that their maximum authorized severity is equal to or higher than the finding's severity; if not, record an "unauthorized_review" violation. Second, compare the review timestamp against the pull request's merge timestamp; if the review occurred after the merge, record a "premature_merge" violation. A single finding can produce both an unauthorized review and a premature merge violation if both conditions hold, but an unreviewed finding should not also be flagged for the other two categories since no review took place at all.

After processing all merged pull requests, compile every violation into a CSV file named `remediation_backlog.csv`. The file must contain exactly these columns in this order: `pr_number`, `violation_type`, `finding_id`, `vulnerability_id`, `severity`, `details`, `priority`. For missing scan violations, the `finding_id`, `vulnerability_id`, and `severity` fields should be left empty, and the `details` field should read "Missing required scan: " followed by the scan type name. For finding-level violations, populate `finding_id` with the numeric finding identifier, `vulnerability_id` with the associated CVE or vulnerability identifier, `severity` with the finding's severity level, and `details` with a short description of the violation. The `priority` column must reflect the value from the violation priority matrix in the scan policy file. Sort the entire backlog first by priority in ascending order, with P1 entries appearing before P2, then by pull request number in ascending order within the same priority level.

Once the file has been written, respond with a compliance summary that states on separate lines the following four statistics using exactly this format: "total_merged_prs: " followed by the count, "compliant_prs: " followed by the count of merged pull requests with zero violations, "non_compliant_prs: " followed by the count of merged pull requests with at least one violation, and "total_violations: " followed by the total number of rows in the backlog. Include a note confirming that the remediation backlog has been saved.
