Your organization manages a fleet of persistent storage volumes across multiple cloud regions and projects. Over time, volumes are created, attached to compute instances, detached, and sometimes left sitting idle, accruing charges without serving any workload. Leadership has asked for a thorough reclamation analysis to identify volumes that have gone unused for an extended period and quantify the potential cost savings from cleaning them up.

Begin by consulting the configuration files available to you. A policy document describes the rules governing this analysis, including the reference date against which all time calculations should be measured, the threshold for how many days a volume must have been unattached before it is considered reclaimable, and a list of volume label values that exempt a volume from reclamation. The policy also specifies that volumes currently under active maintenance windows must be excluded. Pricing information is split across two separate files: one describes the base cost per gigabyte per month for each volume type, and another provides a regional multiplier that adjusts that base cost depending on where the volume is hosted. The estimated monthly savings for a given volume is computed as the volume's size in gigabytes multiplied by the base price for its volume type, then multiplied by the region multiplier.

To determine which volumes are candidates, retrieve the full inventory of volumes and identify those whose current status is available, meaning they are not attached to any instance. For each such volume, look up its attachment event history to find the most recent detach event. The number of days the volume has been unattached is the difference between the reference date and the timestamp of that last detach event. If a volume has no detach events at all, use its creation date instead. Only volumes whose unattached duration strictly exceeds the threshold qualify as candidates.

Once you have the candidate set, cross-reference each volume against the label files scattered across your data directory. These CSV files map each volume to its assigned labels. Any volume carrying at least one label that appears in the policy's exclusion list must be removed from the candidate set. Separately, consult the maintenance schedule files; any volume listed under an active maintenance window must also be dropped.

For every volume that survives these filters, retrieve its snapshot history and record the total number of snapshots associated with it. Then look up the project each volume belongs to: note the project name and department. Also check whether the project has any currently unresolved budget alerts, meaning alerts where the resolved flag is zero.

Compile all of this into a CSV file named `reclamation_report.csv`. The file must contain exactly these columns in this order: `volume_id`, `volume_name`, `project_name`, `department`, `size_gb`, `volume_type`, `region`, `days_unattached`, `last_attachment_date`, `snapshot_count`, `has_active_budget_alert`, `estimated_monthly_savings`. The `last_attachment_date` column should contain the date portion only, formatted as YYYY-MM-DD. The `has_active_budget_alert` column should be True or False. The `estimated_monthly_savings` column should contain the numeric value rounded to two decimal places. Sort the rows by estimated monthly savings in descending order; where two volumes have the same savings, break the tie by days unattached in descending order.

Once the report is written, state in your final response the total number of reclaimable volumes found, the combined storage in gigabytes across all reclaimable volumes, and the total estimated monthly savings formatted to two decimal places in USD.
