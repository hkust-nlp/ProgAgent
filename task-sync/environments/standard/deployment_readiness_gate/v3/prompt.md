You are a release engineer responsible for deciding whether a software release is safe to deploy. A release manifest file in your working directory describes which services are part of the current release and which environments they will be deployed to. A policy file in YAML format specifies the rules that govern the go or no-go decision, and an additional JSON file clarifies how security scan freshness and vulnerability thresholds should be evaluated. Read all of these files carefully before proceeding, because every threshold, every required scan type, and every rule you need lives in those documents rather than being repeated here.

For each service listed in the release manifest, you must evaluate four dimensions. First, retrieve the recent commits on the branch specified by the policy and compute the average test coverage percentage over the number of most-recent commits the policy prescribes. Compare that average against the minimum coverage threshold, noting that the policy defines separate thresholds for critical and standard services, so you will also need to look up each service's criticality level. Second, search for Jira tickets that match the blocking priority levels and statuses defined in the policy. Any ticket that matches both a blocking priority and a blocking status counts as a blocker. Third, pull the configuration drift report for each target environment and identify any drift entries whose severity exceeds the maximum allowed level stated in the policy for the relevant release service. Fourth, for each service, determine which security scan types are required based on its criticality as listed in the policy, then retrieve the scan history and find the most recent scan of each required type that has a passed status. Scans that failed or are still in progress do not count. Check whether the age of that scan, measured from its timestamp to the release date in the manifest, exceeds the allowed number of days, and verify that the number of critical and high vulnerabilities on the scan does not exceed the limits in the policy.

Once you have evaluated every service against every target environment across all four dimensions, produce a CSV file named `deployment_dashboard.csv` in your working directory. Each row in this file represents one service-environment pair. The file must contain the following columns in this order: `service_name`, `environment_name`, `go_nogo`, `test_coverage_avg`, `test_coverage_status`, `jira_blocker_count`, `jira_status`, `config_drift_blocker_count`, `config_drift_status`, `security_scan_status`, `blocking_issues`. The `go_nogo` column should read `GO` when all four checks pass for that pair and `NO-GO` otherwise. Coverage average values must be formatted to exactly two decimal places. Status columns use `PASS` or `FAIL`. The `blocking_issues` column should contain a semicolon-separated list of concise descriptions of each issue found, or be empty if there are none. Rows must be sorted alphabetically by service name, then by environment name.

Separately, create a JSON file named `blocking_issues.json` in the same directory. This file is an array of objects, one per service-environment pair that received a NO-GO decision. Each object must include `service_name`, `environment_name`, and `issues` where issues is a list of short strings describing the individual blockers.

In your final response, state the overall release decision, which is NO-GO if any single pair is NO-GO and GO only if every pair passes. Also state the total number of service-environment pairs evaluated, how many received GO, and how many received NO-GO.
