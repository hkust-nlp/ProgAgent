You are supporting the fraud prevention team for a large online ticket marketplace. Each day the team must review potentially fraudulent purchase transactions before tickets are released for delivery. Your job is to compile today's fraud review queue by scoring every transaction that occurred on the most recent business day in the system, applying a set of risk factors, and producing a prioritized list of flagged orders.

Begin by determining which date requires review. All transactions on that date must be examined. For each transaction you will need to collect several pieces of information from different sources. Device and network session data for a transaction will tell you the geolocation country of the purchasing device and whether a VPN or proxy was detected. Customer verification records, stored as tab-separated text files, contain each customer's verified residential country, which is the authoritative address to use when checking for geographic mismatches. A geographic mismatch occurs whenever the device's country differs from the customer's verified residential country. Event pricing details are stored across a set of JSON files; each entry includes the event identifier, the maximum ticket price, and other event metadata. You will need these maximum prices to determine whether a transaction's amount is anomalously high. Transaction processing records are available as CSV files, each containing a transaction identifier and a binary flag indicating whether the payment processor flagged the transaction as suspicious. A YAML configuration file describes the risk factors, their scoring weights, and the thresholds that separate risk levels. A CSV policy file specifies the maximum number of purchases allowed per day and per rolling seven-day window for each account tier.

Six risk factors must be evaluated for every transaction on the review date. The first factor, called geo_mismatch, applies when the device geolocation country does not match the customer's verified residential country. The second, velocity_violation, applies when the customer's total purchase count on the review date exceeds the daily limit for their account tier, or when their total purchase count across the seven-day window ending on the review date (inclusive) exceeds the seven-day limit for their tier. Use the customer's full purchase history to compute these counts. The third factor, resale_detected, applies when the ticket associated with the transaction has been listed on any resale platform. The fourth, vpn_detected, applies when the device session indicates that a VPN or proxy was in use. The fifth, price_anomaly, applies when the transaction amount strictly exceeds the event's maximum ticket price multiplied by one plus the anomaly threshold percentage defined in the configuration file divided by one hundred. The sixth, processor_flag, applies when the payment processor's binary flag for that transaction equals one.

Each factor that applies contributes its configured weight to the transaction's total risk score. A transaction whose score meets or exceeds the high-risk threshold is classified as HIGH and its recommended action is block_and_investigate. A transaction whose score meets or exceeds the medium-risk threshold but falls below the high-risk threshold is classified as MEDIUM with recommended action manual_review. A transaction whose score is at least ten but below the medium-risk threshold is classified as LOW with recommended action monitor. Transactions scoring below ten are not included in the review queue.

Save the resulting review queue as `fraud_review_queue.csv` with the following columns in this exact order: `transaction_id`, `customer_id`, `risk_score`, `risk_level`, `risk_factors`, `recommended_action`. The risk_score column must contain an integer. The risk_factors column must list the names of all triggered factors for that transaction in alphabetical order, separated by semicolons with no spaces. Sort the rows by risk_score in descending order, breaking ties by transaction_id in ascending lexicographic order.

Once the file is written, provide a summary that states the total number of transactions reviewed on the target date, the count of flagged transactions broken down by risk level as HIGH, MEDIUM, and LOW, and the identifiers of the three highest-risk transactions along with their scores.
