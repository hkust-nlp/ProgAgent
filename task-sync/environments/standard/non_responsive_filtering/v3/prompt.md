Your firm has been retained to manage a large-scale document production in a complex commercial litigation matter. The opposing party has served a series of requests for production, each broken into sub-requests targeting particular custodians, date ranges, and subject matter areas. Every sub-request is associated with a specific topic category and one or more criterion keywords stored in the production database. Your objective is to identify every non-responsive document in the production set and flag it for exclusion from attorney review, thereby reducing overall review volume.

The production universe includes documents drawn from multiple custodians across different departments. Each document carries a Bates-numbered prefix for tracking, and keyword search runs have already been executed against the full collection, capturing which search terms appear in which documents along with their hit counts. However, the raw presence of a keyword in a document does not automatically render it relevant to a given request. Keyword relevance weights, maintained in separate configuration files organized by topic category, determine how significant each keyword is within that category. Only when a keyword's relevance weight for the applicable topic meets or exceeds the minimum weighted relevance score defined in the exclusion rules, and the keyword's hit count for that document meets or exceeds the minimum keyword hit count threshold from those same rules, should the keyword be considered a meaningful match for that criterion.

Custodian participation in each request for production is governed by scope mapping files that record which custodians are considered in scope for which request numbers. Separately, each custodian's current litigation hold status is tracked in status files. When the exclusion rules indicate that an active litigation hold is required, any document whose custodian is not presently on litigation hold must be flagged for exclusion with the reason "no_litigation_hold".

Before assessing responsiveness to the opposing party's requests, two higher-priority exclusion categories must be evaluated. Documents appearing in the privilege log must always be excluded from the production set and assigned the reason "privileged", irrespective of any other factor. Documents whose file format matches one of the excluded file types listed in the exclusion rules configuration must likewise be removed with the reason "excluded_file_type". These two checks take precedence in the stated order: privileged status is evaluated first, then excluded file types, then litigation hold status.

For documents that survive those initial filters, supplementary metadata files record a confidentiality level for each document. If a document's confidentiality level appears among the protected confidentiality levels specified in the exclusion rules, that document must be retained for review regardless of whether it matches any request for production. It should not appear in the exclusion output at all.

All remaining documents must be evaluated against every sub-request across all requests for production. A document is responsive to a sub-request when three conditions hold simultaneously: the document's custodian is in scope for the request number containing that sub-request, the document's creation date falls within the sub-request's date range after symmetrically extending both the start and end dates by the date buffer in days defined in the exclusion rules, and the document possesses at least one keyword hit satisfying both the relevance-weight and hit-count thresholds described above for one of the sub-request's criterion keywords under its topic category. A document that fails to be responsive to every sub-request across all requests should be excluded with the reason "no_rfp_match".

Each excluded document must be assigned exactly one exclusion reason, determined by the highest-priority applicable rule in the following order: "privileged", "excluded_file_type", "no_litigation_hold", "no_rfp_match".

Save the complete set of excluded documents as `exclusion_list.csv` containing the columns `doc_id`, `bates_prefix`, `custodian_name`, `date_created`, `file_type`, and `exclusion_reason`, with rows sorted in ascending order by `doc_id`. Alongside that, produce `exclusion_summary.json` containing the integer-valued keys `total_documents_reviewed`, `total_excluded`, and `total_responsive`, together with an `exclusion_breakdown` object that maps each of the four exclusion reasons to its count. Your final response must include the exact text "EXCLUSION TOTAL: X/Y" where X is the number of excluded documents and Y is the total number of documents reviewed.
