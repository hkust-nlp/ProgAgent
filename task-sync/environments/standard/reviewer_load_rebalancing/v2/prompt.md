Your engineering organization has been experiencing delays in its code review pipeline, and leadership suspects that review assignments are unevenly distributed. You have been asked to perform a thorough analysis of the current review workload across the team, identify which reviewers are overloaded, and produce a concrete rebalancing proposal that reassigns specific pull requests to better-suited colleagues.

Begin by familiarizing yourself with the configuration files that govern the analysis. One file defines the review policy, including the overload threshold (a ratio above which a reviewer is considered overburdened), the number of recent availability-schedule weeks to consider when computing capacity, and a minimum average quality score that any proposed reassignment target must meet based on their historical review completions. Another file contains numerical priority weights keyed by pull request priority level, and a third specifies a capacity multiplier for each role that scales a reviewer's raw available hours into an effective capacity figure. Read and understand all of these before proceeding.

Weekly availability schedules are provided as a series of data files, one per week, each listing every team member's review-available hours for each weekday (Monday through Friday). To compute a reviewer's current capacity, average their total weekly hours across the most recent weeks indicated by the policy's lookback parameter, then multiply by the capacity multiplier for their role.

Using the available tools, retrieve every team member record and every open pull request. Then retrieve all review assignments whose status is either pending or in progress, keeping only those that belong to open pull requests. For each reviewer who has at least one such active assignment, compute a weighted load score by summing, for each of their active assignments, the product of the pull request's priority weight and its complexity score. Divide the weighted load by the reviewer's capacity to obtain an overload ratio. A reviewer is overloaded whenever this ratio strictly exceeds the threshold specified in the policy configuration.

Compile all overloaded reviewers into a file named `overloaded_reviewers.csv` containing the columns `reviewer_id`, `reviewer_name`, `team`, `role`, `weighted_load`, `capacity`, `overload_ratio`, and `pending_review_count`. Sort the rows by overload ratio in descending order. Express weighted load, capacity, and overload ratio as numbers rounded to two decimal places.

Once the overloaded set is established, generate reassignment proposals. For each overloaded reviewer, consider their active assignments in ascending order of priority weight (that is, attempt to reassign the lowest-priority work first). For each candidate assignment, search for the best available target reviewer: someone who is not themselves overloaded, whose list of language specializations includes the pull request's language, who is not the pull request's author, and whose average quality score from historical review completions meets or exceeds the minimum threshold in the policy. Among all eligible candidates, select the one whose projected overload ratio after absorbing the new assignment would be lowest, provided that projected ratio does not itself exceed the overload threshold. When a valid target is found, record the reassignment and update running load tallies so that subsequent proposals reflect earlier ones. Stop proposing reassignments for a given overloaded reviewer once their running ratio drops to or below the threshold.

Save the proposals to `rebalancing_proposal.csv` with columns `pr_id`, `pr_title`, `current_reviewer_id`, `current_reviewer_name`, `proposed_reviewer_id`, `proposed_reviewer_name`, and `reason`. Sort the rows by pr_id in ascending order. The reason column should note the original reviewer's overload status and the proposed reviewer's suitability.

In your final response, state the total number of overloaded reviewers identified, the number of PR reassignments proposed, and the average overload ratio among the overloaded group, formatted to two decimal places.
