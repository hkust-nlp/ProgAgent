You are a water distribution network analyst responsible for identifying zones with persistent, unacceptable water loss. Your organization monitors a network of distribution zones through multiple data sources, and your job is to cross-reference all of them to produce a prioritized repair schedule for zones that require immediate attention.

The first step is to obtain the full list of distribution zones from the system. For every zone in the network, you need to determine whether water loss has remained above a critical threshold for a sustained period. The specific thresholds and time windows you must apply are defined in a policy configuration file available in your files, named `leakage_policy.yaml`. That file specifies the percentage loss threshold, the number of consecutive hours that threshold must be exceeded, and the scoring weights used to prioritize zones. You must read and follow that file precisely rather than assuming any default values.

To assess each zone, begin by retrieving the aggregate flow summary, which gives you the overall loss percentage across the monitoring window. If a zone's aggregate loss is clearly well below the threshold, you can safely skip it and move on. For zones that appear to be near or above the threshold, you must retrieve the detailed hourly flow meter readings. The monitoring data spans multiple days, and the retrieval tool limits each request to a two-day window, so you will need to issue multiple requests covering the full date range from March 10 through March 13, 2025 to assemble the complete hourly picture. For each hour, compute the loss as the difference between inflow and the sum of outflow and billed consumption, expressed as a percentage of inflow. Then scan the hourly sequence to find the longest unbroken run of hours where loss exceeds the threshold. A zone is flagged only when that run meets or exceeds the required consecutive-hour count from the policy file.

Once you have identified all flagged zones, you need to gather several additional pieces of information for each one. Retrieve the detailed zone record to obtain the population served. Query the pressure sensor readings for each day in the monitoring period to compute the fraction of readings that carry an anomaly flag. Query open and in-progress work orders separately for each zone and sum the counts. Separately, locate the pipe inventory files among your available files: they are CSV files whose names begin with `pipe_inventory_batch_` and they contain records for pipes across zones, including material, installation year, and condition score. A companion file called `material_risk_factors.json` provides the risk multiplier for each pipe material, along with formulas for computing age-based and condition-based risk factors. For every pipe belonging to a flagged zone, compute the individual pipe risk as the product of the material multiplier, the age factor, and the condition factor using the formulas in that file, then take the mean of those values as the zone-level pipe risk score.

With all five factors in hand for every flagged zone, the policy file's priority scoring section tells you the weight assigned to each factor: average loss rate, pipe risk score, pressure anomaly rate, open work orders factor, and population impact. Normalize each factor across the set of flagged zones using min-max scaling, multiply by the respective weight, and sum to get the composite priority score. When two zones share the same composite score after rounding to two decimal places, break the tie alphabetically by zone name in ascending order. The recommended action for each zone depends on the composite score: zones at or above 0.7 receive an Emergency Repair designation, those at or above 0.4 but below 0.7 receive Urgent Repair, and those below 0.4 receive Scheduled Maintenance.

Save the final output as `repair_schedule.csv` containing exactly these columns in this order: `priority_rank`, `zone_id`, `zone_name`, `avg_loss_pct`, `max_consecutive_hours_above_threshold`, `pipe_risk_score`, `pressure_anomaly_rate`, `open_work_orders`, `population_served`, `composite_priority_score`, `recommended_action`. All numeric fields should use two decimal places except `pressure_anomaly_rate` which uses four decimal places and integer fields which remain integers. Rows should appear in descending composite priority score order, with priority rank starting from one.

In your final response, list every flagged zone by name along with its average loss percentage to two decimal places, its composite priority score, and the recommended action. Confirm that the repair schedule file has been written.
