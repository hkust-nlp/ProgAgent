You are tasked with validating the feasibility of a set of proposed passenger train schedules across a rail network. Several batch files containing schedule proposals have been placed in your working directory. Each proposal specifies a train service code, a route section identifier, a date, and proposed departure and arrival times. Your objective is to cross-reference every proposal against known operational constraints, identify all conflicts, and produce a prioritized set of rescheduling recommendations.

The tools at your disposal allow you to query train service details including operator, type, and priority class, to look up route section information including any associated junction, to retrieve maintenance possession blocks for a given section, to obtain junction capacity data, and to pull historical punctuality records for each section. In addition to these tools, your working directory contains configuration files that govern the conflict detection rules, the formula for computing rescheduling priority scores, and the thresholds used to classify punctuality risk levels. You should explore the directory to locate these files and extract their parameters before proceeding.

Three categories of conflict must be detected for every proposal. The first category covers maintenance conflicts. When a proposed schedule's time window overlaps with a maintenance possession block on the same route section, the conflict is classified as a maintenance overlap. If the proposal does not directly overlap but falls within the configured buffer zone around the maintenance window, it is classified as a maintenance buffer conflict. To check for overlap, construct each proposal's full datetime window by combining its date with its departure time and arrival time, then compare against the maintenance block's start and end datetimes. Two windows overlap when the proposal departs before the maintenance block ends and arrives after the maintenance block starts. For the buffer check, extend the maintenance window on both sides by the number of minutes specified in the rules configuration and apply the same overlap logic to the extended window. Each proposal should be checked against all maintenance blocks on its section. If the proposal directly overlaps any block, record a single maintenance overlap conflict. If it does not overlap any block but falls within the buffer of at least one, record a single maintenance buffer conflict.

The second category is junction overload. Look up each proposal's route section to determine whether it has an associated junction. When a junction is present, determine all clock-hour windows the proposal spans, where each window runs from the top of an hour to the top of the next hour. Collect all proposals that pass through the same junction and tally how many appear in each clock-hour window. If the count in any window strictly exceeds the junction's capacity per hour multiplied by the threshold ratio from the configuration, every proposal contributing to that overloaded window should receive a junction overload conflict. A proposal should receive at most one junction overload conflict even if it contributes to multiple overloaded windows.

The third category is punctuality risk. For each proposal, retrieve all historical punctuality records for its route section. Compute the section's average on-time percentage across every recorded period. If this average falls at or below the high-risk threshold extracted from the risk thresholds configuration file, flag the proposal with a punctuality risk conflict. The threshold configuration file marks which risk level should be flagged as a conflict.

Once all conflicts have been identified, compute a rescheduling priority score for each conflict entry. The priority scoring formula and its parameters are specified in the priority matrix configuration file. The inputs to the formula are the severity weight corresponding to the conflict's severity level, the train's priority class as returned by the train lookup tool, and the section's average delay in minutes computed from the historical punctuality records across all periods. If no punctuality data exists for a section, treat the average delay as zero. The severity assigned to each conflict type is defined in the conflict rules configuration file.

Save the first deliverable as a file named conflict_report.csv with the following columns in this exact order: conflict_id, proposal_id, train_service_code, section_name, conflict_type, severity, details. Sort the rows first by severity in the order critical then major then moderate then minor, and within each severity level by proposal_id in ascending lexicographic order. Assign conflict_id values sequentially as C0001, C0002, and so on after sorting. The details column should contain a brief human-readable description of the specific conflict.

Save the second deliverable as a file named rescheduling_recommendations.json. This file must contain a JSON array of objects, each with the fields rank, proposal_id, train_service_code, conflict_type, severity, priority_score, and recommendation. Round every priority_score to exactly two decimal places. Sort the array by priority_score in descending order, breaking ties by proposal_id in ascending lexicographic order. Assign the rank field sequentially starting from one in this sorted order. The recommendation field should contain a brief suggested action.

In your final response, state the total number of conflicts identified, provide the count broken down by conflict type using the format maintenance_overlap: N, maintenance_buffer: N, junction_overload: N, punctuality_risk: N, and list the top three rescheduling recommendations showing for each the rank, proposal_id, and priority_score.
