You are the on-call analyst at a residential care facility that uses wearable and room-mounted motion sensors to generate automatic fall alerts for elderly residents. The system is known to produce a significant number of false positives, and every pending alert must be investigated before the nightly report goes out to emergency contacts. Your job is to review every alert currently marked as pending, determine whether it represents a genuine fall or a false alarm, and produce a clean incident report ready for distribution.

Begin by retrieving the full set of pending alerts through the alert-listing interface, paging through all results until none remain. For each alert you must gather its detailed record, which will include the identifier of the sensor device that triggered it. A device-to-room mapping file in the working directory will tell you which room and building zone corresponds to that device. Once you know the zone, locate the matching baseline activity profile file for that zone; it contains the historical maximum acceleration, mean acceleration, gyroscopic ceiling, and active-hours window for every room in the zone. You will also need the resident profile for the person linked to the alert, as well as the caregiver visit log for that resident on the alert date and the audio event log for the room within the relevant time window around the alert.

Determining whether an alert is a true fall requires fusing all of these signals according to the thresholds and rules stored in the configuration files in the working directory. One file defines the acceleration deviation factor and minimum magnitude, the caregiver presence window in seconds, and the audio confirmation window, minimum confidence, and list of confirming audio event types. A separate text file lists the caregiver visit types whose physical assistance routinely triggers motion sensors and should therefore be treated as exempt when evaluating caregiver overlap. A CSV file defines the severity tiers by specifying, for each tier, the minimum peak acceleration required and whether audio confirmation is also mandatory for that tier; it also assigns each tier a numeric rank used for ordering.

For each pending alert, compute the peak acceleration magnitude from the motion readings associated with that alert, which is the Euclidean norm of the three accelerometer axes at the highest-magnitude sample. Compare the peak to the threshold, which is the greater of the room baseline maximum multiplied by the deviation factor, or the global minimum magnitude. If the peak does not exceed the threshold the alert is a false positive. If it does, check whether any caregiver visit of an exempt type was physically present, meaning the actual arrival time is no later than the alert timestamp plus the caregiver presence window and the actual departure time is no earlier than the alert timestamp minus the same window. Also check whether any audio event of a confirming type with confidence at or above the minimum was recorded in the same room within the audio confirmation window on either side of the alert timestamp. An alert whose motion exceeds the threshold is verified as a true incident when either no exempt caregiver was present or the audio evidence confirms the fall despite the caregiver overlap. If an exempt caregiver was present and there is no confirming audio, the alert is a false positive regardless of the motion reading.

For every verified incident, assign a severity level by walking the severity tiers from the highest rank downward: assign the first tier whose acceleration minimum the peak meets, skipping any tier that requires audio confirmation if no confirming audio was found.

Once every pending alert has been classified, write an output file called `incident_report.csv` into the working directory. It must contain one row per pending alert, and the columns, in this exact order, must be `alert_id`, `resident_name`, `room_number`, `alert_timestamp`, `peak_acceleration`, `baseline_max`, `severity_level`, `verification_status`, `contributing_factors`, `emergency_contact_name`, `emergency_contact_phone`. The peak acceleration value must be rounded to exactly four decimal places. The severity level column should read `critical`, `high`, `medium`, or `low` for verified incidents, and `n/a` for false positives. The verification status column must contain exactly `verified` or `false_positive`. The contributing factors column must list three assessments in the fixed order of motion assessment, caregiver assessment, and audio assessment, separated by a semicolon and a space. The motion token is `motion_exceeded` when the peak exceeded the threshold or `motion_within_baseline` otherwise. The caregiver token is `caregiver_exempt_present` when an exempt visit overlapped or `no_caregiver_overlap` otherwise. The audio token is `audio_confirmed` when a qualifying event was found or `no_audio_confirmation` otherwise. Emergency contact name and phone come from the contacts reference file in the working directory, using the primary contact for the resident linked to each alert. Rows must be sorted first by severity rank in ascending order, using the rank numbers from the severity tiers file, with false-positive rows assigned rank five, and then by alert timestamp ascending as a tiebreaker.

After writing the report, state in your final response the total count of alerts you reviewed, the count you confirmed as true fall incidents, and the count you classified as false positives.
