Your organization manages a large fleet of feature flags across multiple services and deployment environments. A security compliance review has been initiated, and you are responsible for conducting a thorough audit of every feature flag currently in the system. The goal is to identify all flags whose configurations violate internal compliance policies, then produce a remediation roster that the security team can act on.

The compliance rules you must enforce are defined in a YAML policy file that specifies the minimum employee clearance level required to own a flag in each environment tier, as well as the targeting policy, change management requirements, approved maintenance windows, and a severity classification scheme per environment. A separate CSV file lists which services are classified as sensitive, and another CSV file describes the permissions associated with each Active Directory group, including which environments that group is authorized to modify. A Markdown procedures document defines the exact remediation action text that must be recorded for each type of violation.

Five categories of violation must be detected. First, a clearance violation exists whenever a flag's owner holds a clearance level below the minimum required for the flag's environment, as stated in the policy. Second, a targeting violation exists when none of the Active Directory groups targeted by a flag's rules overlap with the groups the flag's owner belongs to, unless the owner holds membership in one of the groups explicitly listed as exempt in the targeting policy. Targeting rule definitions are stored in JSON batch files that map each flag to its targeted groups. Third, a missing-ticket violation exists when a flag deployed to an environment that requires change management has audit log evidence of a modification or toggle action yet no approved change ticket on record. Fourth, an out-of-window change violation exists when a flag in a production or production-critical environment has a modification or toggle audit entry whose timestamp falls outside the approved maintenance windows described in the policy. Weekday and weekend windows differ and all times are in UTC; a single out-of-window entry is sufficient to flag the violation for that flag. Fifth, a sensitive-service approval violation exists when a flag belongs to a sensitive service, has at least one approved change ticket, yet none of those tickets were approved by an employee who is a member of the Security Active Directory group.

To carry out the audit you will need to retrieve every feature flag, look up the employee record and group memberships for each flag owner, examine change tickets and audit logs for relevant flags, and cross-reference all of that with the policy files and targeting-rule batch files. Each flag may carry more than one violation, and each violation should appear as its own row.

Once the analysis is complete, save the results as `remediation_roster.csv`. The file must contain exactly these columns in this order: `flag_id`, `flag_name`, `service`, `environment`, `owner_name`, `owner_id`, `violation_type`, `severity`, `remediation_action`. The `violation_type` field must use one of the exact labels: `CLEARANCE_VIOLATION`, `TARGETING_VIOLATION`, `MISSING_TICKET`, `OUT_OF_WINDOW_CHANGE`, `SENSITIVE_NO_SECURITY_APPROVAL`. The `severity` field must reflect the environment-based severity mapping from the policy file. The `remediation_action` field must contain the exact text defined in the remediation procedures document for the corresponding violation type. Rows must be sorted first by severity in descending order of urgency, meaning critical comes before high, then medium, then low, and within the same severity level rows must be sorted by flag ID in ascending lexicographic order.

In your final response, state the total number of violations identified, report how many unique flags are affected, and provide a breakdown of the count for each of the five violation types.
