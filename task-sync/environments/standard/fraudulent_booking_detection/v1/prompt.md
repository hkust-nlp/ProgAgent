The hotel's security division requires a comprehensive daily fraud risk assessment covering every reservation scheduled for check-in on a specific review date. That date, along with all scoring weights and activation thresholds, is defined in a YAML configuration file stored in your working directory. Begin by locating and reading this configuration so you know which date to target and how each risk factor is scored.

For every reservation whose check-in falls on the review date, you must individually evaluate the associated guest against multiple risk dimensions, combining information from both tool queries and files in the working directory. No single source contains everything needed; the assessment depends on cross-referencing structured query results with data extracted from local files.

Start by retrieving the full set of reservations for the configured review date. For each reservation, look up the guest's identity details and obtain their identity document number. Then check that document number against the fraud blacklist database; a confirmed match carries the heaviest weight in the scoring model. Next, retrieve the payment method linked to the reservation and examine two properties: whether it is a prepaid instrument, and whether its accumulated fraud flag count meets or exceeds the minimum defined in the configuration. Separately, determine how many no-show incidents are on record for the guest; if that count reaches the configured minimum, apply the corresponding score.

Beyond tool-based queries, three categories of files in your working directory supply information that cannot be obtained through any other channel. JSON files contain identity document scan results organized in batches, each entry recording a guest identifier and a numeric scan confidence value; if the confidence for a particular guest falls below the configured floor, the low-confidence penalty applies. CSV files hold transaction logs referencing payment method identifiers, with each row indicating whether the transaction was a chargeback; compute the chargeback ratio for each relevant payment method as the number of chargeback transactions divided by the total number of transactions for that method, and if the resulting ratio meets or exceeds the configured threshold, add the corresponding score. Finally, text-formatted booking pattern summaries list each guest's recent booking activity, indicating whether the guest has been flagged for rapid booking; if the flag reads yes, the rapid-booking weight is added.

A reservation's total risk score is the arithmetic sum of every applicable factor weight. Only reservations whose total score meets or exceeds the cutoff specified in the configuration belong on the daily review list; all others are excluded entirely.

Produce a file named `daily_fraud_review.csv` with columns in exactly this order: `reservation_id`, `guest_name`, `document_number`, `risk_score`, `risk_factors`, `priority`. Format each guest's name as their first name followed by a single space and then their last name. In the `risk_factors` column, list every triggered factor using the exact key names from the configuration's scoring weights section, joined by semicolons with no surrounding spaces, sorted alphabetically. Assign a `priority` of `critical` when the risk score is sixty or above, and `high` for every other entry on the list. Sort rows by `risk_score` in descending order; where two reservations share the same score, break the tie by `reservation_id` in ascending order.

Once the review list is complete, state in your final response the total number of flagged reservations and list all reservation IDs classified as critical priority in ascending order, formatted exactly as follows: "Flagged: N reservations. Critical: R00001, R00002" replacing the example IDs with the actual ones, or "Flagged: N reservations. Critical: none" if no entries qualify as critical.
