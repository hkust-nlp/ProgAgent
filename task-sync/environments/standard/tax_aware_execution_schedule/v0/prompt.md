Your firm's portfolio management division has prepared a series of proposed rebalancing trades across all client accounts, and every one of them must be reviewed for tax efficiency before it can go to execution. The proposed trades are organized into CSV files, each containing a batch of trades with fields for the trade identifier, client identifier, security identifier, the proposed action (buy or sell), the proposed quantity, an urgency rating from one to five, and the reason for the rebalancing. You will find these files alongside several configuration documents when you explore the directory you are working in.

To evaluate each trade you will need to retrieve client information, including tax status, filing status, jurisdiction, and account type, through the data retrieval functions available to you. You will also need to look up lot-level cost basis records for any security a client is proposed to sell, year-to-date capital gains summaries, and recent transaction history. Security details, including the current market price, must likewise be obtained through the provided functions.

Four configuration documents govern the analysis. A JSON file details the applicable federal and state tax rates for short-term and long-term capital gains across different jurisdictions. A YAML file specifies the wash sale rules, including the federal lookback period and which account types are subject to them. A second YAML file lays out the rebalancing policy, including the lot selection method, the maximum year-to-date short-term and long-term gain thresholds per client, the reference date for the analysis, the base execution date for non-deferred trades, and the defer date for trades that must be postponed. A markdown reference document describes how those gain thresholds should be adjusted according to a client's filing status before any comparison is made; you must apply the multipliers it specifies.

For each proposed trade, assign exactly one flag. Clients whose accounts carry a tax status of tax_deferred or tax_exempt always receive the flag TAX_ADVANTAGED regardless of any other analysis, and their estimated tax impact is zero. For sell trades in taxable accounts, begin by selecting lots using the method stated in the rebalancing policy (sorting by cost basis per share in descending order and greedily filling the proposed quantity). If the total available lot quantity is less than the proposed quantity, use only what is available. Compute the total gain or loss across the selected lots by comparing each lot's cost basis per share to the security's current market price. If the trade results in a net loss and there has been a purchase of the same security by the same client within the wash sale lookback window measured backward from the reference date, flag it as WASH_SALE_RISK. If instead the trade results in a net gain, first check whether the client's existing year-to-date positive short-term realized gains plus the short-term component of this trade's gain would exceed the filing-status-adjusted short-term threshold, or whether the analogous long-term sum would exceed the adjusted long-term threshold; if either condition holds and the relevant trade gain component is positive, flag the trade as EXCESSIVE_GAIN. Failing that, if the selected lots include any short-term lots (held fewer days than the long-term holding period specified in the policy as measured from purchase date to the reference date) while at least one unselected long-term lot of the same security for the same client exists, and the trade overall is a gain, flag it as SUBOPTIMAL_LOT. Otherwise flag it PASS. For buy trades in taxable accounts, check whether the client has any capital gains records showing a realized loss on the same security with a sale date within the lookback window from the reference date; if so, flag the trade as WASH_SALE_RISK, otherwise PASS.

Execution dates depend on the flag. Trades flagged PASS, SUBOPTIMAL_LOT, or TAX_ADVANTAGED receive the base execution date from the policy. Trades flagged EXCESSIVE_GAIN receive the defer date. For WASH_SALE_RISK trades, find the date of the most recent triggering event (the latest buy transaction date for sell-side wash sales, or the latest loss sale date for buy-side wash sales), add the lookback period plus one day, and use whichever is later between that result and the base execution date.

For every sell trade, record the identifiers of the lots used in the selection, listed in the order they were selected, separated by the pipe character. For buy trades or sells with no available lots this field is empty. The estimated tax impact equals the sum, over all selected lots, of the per-lot gain multiplied by the applicable combined federal-plus-state tax rate, where the federal component is the short-term rate when the lot's holding period is below the long-term threshold and the long-term rate otherwise; the state component comes from the client's jurisdiction. For buy trades the estimated tax impact is zero. Round every tax impact value to two decimal places.

Once every proposed trade has been analyzed, save the full results to a file called execution_schedule.csv containing the following columns in exactly this order: trade_id, client_id, security_id, action, quantity, execution_date, flag, flag_reason, recommended_lot_ids, estimated_tax_impact. The quantity column reflects the executable amount, which is the lesser of the proposed quantity and the total available lot holdings for sell trades, or the proposed quantity for buy trades. Sort rows first by execution_date ascending, then by trade_id ascending.

Your final response must include a plain-text summary with each of the following statistics on its own line in the format "Label: value". Use exactly these labels: Total trades, Flagged trades (counting only WASH_SALE_RISK plus EXCESSIVE_GAIN plus SUBOPTIMAL_LOT), WASH_SALE_RISK, EXCESSIVE_GAIN, SUBOPTIMAL_LOT, TAX_ADVANTAGED, PASS, and Total estimated tax impact (formatted as a dollar amount with two decimal places, e.g. $1234.56).
