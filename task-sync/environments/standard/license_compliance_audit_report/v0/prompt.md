Your organization is preparing for an upcoming product release cycle and needs to ensure that every third-party software component across all active projects complies with the corporate open-source license policy. Several recent incidents involving license changes in upstream dependencies and expired legal exceptions have highlighted gaps in the current compliance posture, and leadership has asked for a comprehensive audit before any release gates open.

Begin by reviewing the approved license registry file, which lists every license the organization has evaluated and classified into one of three tiers: approved licenses that may be used freely, restricted licenses that carry conditions on where they may be deployed, and denied licenses that cannot be used without a valid legal exception. Alongside this, review the compliance policy configuration that specifies how risk scores are computed and what action thresholds apply. The risk score for a component is calculated by multiplying the base risk weight associated with its license's risk level by the criticality multiplier of the project it belongs to and then by a vulnerability factor derived from the number of known vulnerabilities reported for that component in the most recent software composition analysis scans. The vulnerability factor equals one plus one-tenth of the vulnerability count, capped at three. All of these parameters, weights, and thresholds are defined in the policy configuration.

Separately, gather vulnerability and scan confidence data from the software composition analysis scan reports distributed across multiple batch files. Each batch file covers a subset of components and provides the detected license, vulnerability count, maximum CVSS score, the scanner that produced the finding, and the confidence percentage. These scan results are the authoritative source for vulnerability counts used in risk score calculation.

Once the policy rules and scan data are in hand, enumerate every project using the available tooling and retrieve the full list of components for each project, paging through results as necessary. For each component, determine its license, look up that license in the registry to obtain its risk level and category, and then cross-reference the component against the scan data for its vulnerability count. Use the project's criticality level together with the license risk level and vulnerability count to compute the risk score according to the policy formula.

For every component whose license falls in the denied tier, query its legal exception history. The most recent exception ticket supersedes any earlier ones and represents the current state. A component with a denied license is considered compliant only if its most recent exception has an approved status and its expiry date has not passed relative to the reference date specified in the policy. If the most recent exception is expired or if it was filed as approved but its expiry date has already passed, the component requires exception renewal. If the most recent exception is pending, the component is awaiting review. If the exception was denied or if no exception exists at all, the component is non-compliant and the required action depends on the risk score: components at or above the replacement threshold must be replaced, while those below it should obtain a new exception. The specific thresholds are documented in the policy configuration.

For components under a restricted license, check the deployment environment. Restricted licenses deployed to production or staging environments require a legal review. Restricted licenses in development, testing, or internal-tools environments are considered acceptable and need no action.

On top of this, examine the version change history for every non-approved-license component. Any component whose history includes a license change event within the lookback window defined in the policy, measured backward from the reference date, must be flagged for re-evaluation regardless of its current exception status, because the exception may have been granted under the prior license terms.

Components with approved licenses that have no recent license change are fully compliant and should not appear in the report. Likewise, restricted-license components not deployed to production or staging and without a recent license change are compliant.

Produce a file called `compliance_report.csv` containing one row for every component that is not fully compliant. The file must use the following columns in this exact order: `component_name`, `project_name`, `license_spdx`, `license_category`, `deployment_env`, `compliance_status`, `risk_score`, `action_required`. The compliance status must be one of `non_compliant`, `exception_expired`, `exception_pending`, `exception_denied`, `restricted_deployment`, or `license_changed`. The action required must be one of `replace`, `renew_exception`, `obtain_exception`, `pending_review`, `legal_review`, or `re_evaluate`. Risk scores must be formatted to exactly two decimal places. Sort the rows by risk score in descending order, breaking ties by component name in ascending alphabetical order.

In your final response, state the total number of components analyzed across all projects, the number of components flagged for compliance issues, and the number of components requiring immediate replacement.
