You are a fraud analyst responsible for screening every pending credit card application and determining which ones should be rejected. The application data arrives in numbered batch files named with a sequential pattern; each batch is a CSV containing the application identifier, the channel through which the submission arrived, any referral code the applicant supplied, the income figure the applicant self-reported, the document verification status, and the timestamp of submission. Read every batch file to compile the full list of applications under review.

Separately, four configuration files govern the screening logic. A YAML policy file defines the risk threshold and the individual risk factors, each identified by a code from R01 through R10. Every factor specifies the conditions under which it applies and the number of risk points it contributes. A JSON rules file lists the referral-code prefixes and email domains considered suspicious. A CSV reference file maps each reason code to a human-readable name and category. A JSON regional risk map assigns every U.S. state abbreviation a tier of high, medium, or low.

For each application you must gather information from multiple sources. The bank's internal records hold the applicant's name, SSN last four digits, email address, phone number, state, ZIP code, requested credit limit, verified annual income, employment status, and employer. A credit bureau service provides the credit score, number of open and delinquent trade lines, total delinquency amount, years of credit history, total outstanding debt, a bankruptcy flag, and hard inquiries in the last six months. A device intelligence service reports the device hash, IP address, IP country, whether a VPN or proxy was detected, browser, operating system, and session duration. A fraud-screening service checks each applicant's SSN last four, email domain, and phone prefix against a database of known fraudsters and returns any matches together with fraud type and severity. A velocity service reports how many other applications share the same device hash or IP address as the application in question.

Apply the following risk-factor logic to every application. R01 triggers when the credit score falls below the credit-score threshold stated in the policy. R02 triggers when the self-reported annual income exceeds the verified annual income by more than the discrepancy threshold expressed as a fraction of verified income. R03 triggers when a VPN or proxy is detected and the requested credit limit meets or exceeds the limit threshold for that factor. R04 triggers when the fraud-screening service returns at least one match; if multiple matches exist, use the highest severity among them and award the corresponding points from the severity-to-points mapping in the policy. R05 triggers when the velocity count meets or exceeds the velocity threshold. R06 triggers when the document verification status is failed. R07 triggers when the bankruptcy flag is set and the requested credit limit meets or exceeds the limit threshold for that factor. R08 triggers when the applicant's state is classified as high risk in the regional map and the credit score falls below the credit-score threshold defined for that factor. R09 triggers when the referral code begins with any of the suspicious prefixes listed in the rules file. R10 triggers when the email domain matches any of the suspicious domains listed in the rules file.

Sum the points from all triggered factors for each application. Any application whose total risk score meets or exceeds the risk threshold stated in the policy must be rejected. Once you have identified every rejected application, produce a CSV file named `rejection_roster.csv` containing exactly the columns `app_id`, `applicant_name`, `risk_score`, `reason_codes`, and `decision`. The reason codes column must list every triggered factor code in alphabetical order, separated by semicolons with no spaces, for example R01;R06;R08. The decision column must read REJECT for every row. Sort the rows by risk score in descending order; where two applications share the same risk score, sort them by application identifier in ascending lexicographic order.

After writing the file, state in your final response the total number of applications reviewed, the total number rejected, and the rejection rate expressed as a percentage rounded to one decimal place followed by a percent sign.
