You are a fraud analyst for a large online game's trust and safety team. Your task today is to process all pending wealth-influx alerts in the system, investigate the associated player accounts, and produce a daily suspicious-accounts report ready for manual review by senior analysts.

Begin by reading the fraud scoring configuration, which specifies the analysis date to use as the reference point for all date-based computations, the weights assigned to each scoring factor, the thresholds that govern when a factor triggers, the base scores tied to alert severity levels, and the multipliers that determine recommendation tiers. You will also find a rarity configuration file that documents item-value ranges and level brackets for each rarity tier, and a region risk file that maps each server region to a risk multiplier applied to the final score.

Retrieve every wealth alert currently marked as pending. For each unique player who has at least one pending alert, you must investigate and compute a fraud score using the following methodology.

Start with a base score determined by the highest-severity pending alert for that player, using the alert base scores from the configuration. Then evaluate the player's account age: if the number of days between their registration date and the analysis date is less than the new-account threshold defined in the configuration, add the new-account bonus. Next, count all marketplace listings where the player is the seller and the listing date falls within the trade-frequency period (the most recent N days as specified by the threshold). If that count exceeds the trade-frequency threshold, add the high-frequency-trading weight.

For each of those recent seller listings, perform two additional checks. First, determine the market reference price for the listed item by averaging the three most recent price snapshot observations available in the price history data files; if fewer than three snapshots exist use however many are available, and if none exist fall back to the item's base value obtained from the item details. If the listing price exceeds the price-anomaly multiplier times the market reference price, add the price-anomaly-per-listing weight. Second, compare the item's level requirement against the player's account level; if the requirement exceeds the level, add the level-mismatch-per-listing weight.

Separately, examine the session log files to count how many distinct IP addresses the player has used. If that count exceeds the multi-IP threshold, add the multi-IP-sessions weight. Also sum the influx amounts across all of the player's pending alerts; if the total exceeds the wealth-influx base, compute the integer part of the quotient of the excess divided by the base and multiply it by the wealth-influx-severity weight. Finally, count any prior account flags recorded in the historical account-flag files and add the prior-flag-per-incident weight for each flag found.

Once all individual factor scores have been summed, multiply the total by the region risk multiplier corresponding to the player's region. Round the resulting fraud score to one decimal place. A player is considered suspicious only when this final score meets or exceeds the suspicious-score threshold.

For each suspicious player, determine the primary evidence by identifying which scoring factor (excluding the alert base score) contributed the most points before the region multiplier was applied. If two factors tie, choose the one whose name comes first alphabetically. Also assign a recommendation: if the score is at or above the threshold multiplied by the block multiplier, the recommendation is "block"; if at or above the threshold multiplied by the restrict multiplier, it is "restrict"; otherwise it is "investigate".

Save the results as `suspicious_accounts_report.csv` containing exactly the columns `player_id`, `username`, `fraud_score`, `alert_type`, `primary_evidence`, `recommendation` in that order. The rows must be sorted by `fraud_score` in descending order with ties broken by `player_id` in ascending order. Only suspicious accounts (those meeting the threshold) should appear in this file. The `alert_type` column should reflect the alert type of the highest-severity pending alert used for the base score.

Your final response must state the total number of unique accounts reviewed (all players with at least one pending alert), the total number of suspicious accounts identified, and the breakdown of recommendation tiers: how many are to be blocked, how many restricted, and how many marked for investigation.
