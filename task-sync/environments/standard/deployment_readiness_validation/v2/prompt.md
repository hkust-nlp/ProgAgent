Your organization is preparing a deployment release for a batch of microservices. Each service that is a candidate for this release has a corresponding deployment request file sitting alongside the configuration documents you will need to consult. These request files come in various formats and each one specifies the service name, its numeric service ID, the target Kubernetes namespace, the amount of CPU cores and memory (in GB) being requested, the container image tag, and other operational metadata. Your job is to evaluate every pending deployment request against four readiness dimensions and produce a definitive go or no-go decision for each service.

The first dimension is vulnerability posture. For each candidate service, retrieve its full vulnerability scan report using the service's numeric ID. Not every reported CVE counts against the service — vulnerabilities whose status is listed in the policy file's excluded statuses should be disregarded entirely. Among the remaining actionable vulnerabilities, count how many are of critical severity and how many are of high severity, then compute a cumulative risk score by summing the per-severity risk values defined in the risk scoring reference file for every actionable vulnerability. A service fails the vulnerability check if any of three conditions hold: the count of actionable critical vulnerabilities exceeds the policy maximum, the count of actionable high vulnerabilities exceeds the policy maximum, or the cumulative risk score exceeds the policy ceiling. There is also a priority-level override: services whose priority is designated as critical in the service registry are held to a stricter standard — they must have zero actionable high-severity vulnerabilities regardless of the general threshold.

The second dimension is infrastructure capacity. For each candidate service you must verify that deploying it will not push the target namespace's resource utilization beyond the allowed ceiling. The policy file specifies which resource types must be checked and the maximum post-deployment utilization ratio. For each required resource type, retrieve the current quota limit and usage for the target namespace, then add together the current usage, the resources being requested in the deployment file, and the reserved buffer amount found in the namespace resource buffer configuration for that namespace and resource type. Divide the resulting sum by the quota limit to obtain the projected utilization. If the projected utilization exceeds the policy threshold for any required resource type, the service fails the resource check.

The third dimension is dependency health. Retrieve the dependency list for each candidate service. If a dependency is tagged as critical in criticality and the policy states that critical dependencies must be healthy, then any critical dependency whose health status is not healthy causes the service to fail. Additionally, if the policy says that an unhealthy dependency blocks deployment, then any dependency regardless of criticality that has a health status of unhealthy also causes a failure. For standard-criticality dependencies, compute the ratio of those whose health status is degraded or unknown to the total count of standard dependencies. If this ratio exceeds the policy maximum for degraded standard dependencies, the service fails the dependency check.

The fourth dimension is change request approval. Retrieve the change request records for each candidate service. The service passes this check if and only if at least one change request exists whose status matches one of the policy's required statuses and whose number of approvals meets or exceeds the policy's minimum approval count. If no such change request is found, the service fails.

A service receives a GO decision only when it passes all four checks. If it fails any check, the decision is NO-GO.

Once you have evaluated every pending deployment request, save the results as `deployment_manifest.json`. This file must contain a top-level object with two keys. The first key, `services`, holds a JSON array where each element is an object with the fields `service_name`, `service_id`, `decision` (the string GO or NO-GO), `vulnerability_risk_score` (a number rounded to two decimal places), `vulnerability_check` (PASS or FAIL), `resource_check` (PASS or FAIL), `dependency_check` (PASS or FAIL), `cr_check` (PASS or FAIL), and `blockers` (an array of short strings describing each reason the service was blocked, or an empty array for GO services). The second key, `summary`, holds an object with `total_services`, `go_count`, and `nogo_count` as integer fields.

In your final response, list every evaluated service in alphabetical order by name, showing the service name followed by its decision and the four individual check results and its vulnerability risk score. After the per-service listing, provide two summary lines: one listing all GO services in alphabetical order separated by commas, and one listing all NO-GO services in alphabetical order separated by commas.
