You are the dispatch coordinator for a field service company that handles maintenance and repair requests across multiple zones in a metropolitan area. Each week, all pending service requests must be matched to available technicians based on their skill certifications, and the parts each job requires must be sourced from an appropriate warehouse, all while keeping overall travel time and part-sourcing delays as low as possible.

You will find batch CSV files containing supplementary details about individual service requests that are not available through the data retrieval functions. Each record in these files provides the customer's tier classification (platinum, gold, silver, or bronze), the customer's preferred scheduling day, and any special instructions. A CSV file provides a matrix of travel times in minutes between every pair of service zones, with zone names along both axes. A YAML configuration file lays out the dispatch policy: the minimum certification level required at each priority level, multipliers associated with each customer tier, the maximum number of assignments a single technician may receive per day and per week, the list of valid scheduling days, a reference date that determines whether a certification has expired, and a numeric hierarchy mapping each certification level to a rank. A JSON file defines two cost weights and includes a description of how the assignment cost formula works and the order in which requests should be dispatched. Another JSON file maps each zone to a seasonal demand factor for the current period. A YAML file maps each warehouse identifier to its name and the zone it is located in.

To retrieve information about pending service requests you should query the appropriate function, which returns paginated results including each request's identifier, customer name, zone, required skill, priority level, estimated duration, status, and creation date. A separate function lists active technicians in pages, returning each technician's identifier, name, home zone, years of experience, and active status. Another function accepts a technician identifier and returns all of that technician's certifications, each with a skill name, certification level, and expiry date. One function takes a request identifier and returns the parts that request requires along with the quantity needed. Finally, a function accepts a part identifier and a warehouse identifier and returns the current quantity on hand together with the estimated reorder lead time in days.

The dispatching process works as follows. For every pending request, compute an effective priority equal to the request's numeric priority level multiplied by the customer tier multiplier from the dispatch policy and then multiplied by the seasonal demand factor for the request's zone. Sort all pending requests in descending order of this effective priority, breaking ties by request identifier ascending, and process them in that sequence. For each request, look up the minimum certification level required for the request's priority as defined in the dispatch policy, then identify every active technician who holds a certification in the request's required skill at or above that minimum level, where a certification is considered valid only if its expiry date is on or after the reference date given in the dispatch policy, and the technician has not yet reached the weekly assignment cap. For each eligible technician, look up the travel time from the technician's home zone to the request's zone. For each warehouse, determine whether every required part is available in sufficient quantity; if any part falls short, the part wait in days for that warehouse equals the maximum reorder ETA among the parts that are insufficient, and if all parts are sufficient the wait is zero. The warehouse travel component is the travel time from the warehouse's zone to the request's zone. The total assignment cost for a given technician-warehouse pair equals the travel time weight multiplied by the sum of the technician's travel minutes and the warehouse's travel minutes, plus the wait time weight multiplied by the part wait days multiplied by sixty. Among all eligible technician-warehouse pairs for the request, select the one with the lowest total cost, breaking ties first by technician identifier ascending and then by warehouse identifier ascending. Schedule the chosen assignment on the customer's preferred day if the selected technician still has capacity on that day under the daily cap; if not, try each scheduling day from Monday through Friday in order, skipping the preferred day that was already attempted, and pick the first day with available capacity. Update the technician's daily and weekly assignment counts accordingly. If no feasible assignment exists for a request because no technician qualifies or every qualified technician has exhausted all day slots, the request is left unassigned.

Once every pending request has been processed, save the final roster as `assignment_roster.csv` with these columns in this exact order: `request_id`, `technician_id`, `warehouse_id`, `scheduled_day`, `travel_time_minutes`, `part_wait_days`, `assignment_cost`. The travel time value should be an integer representing the combined technician-to-request and warehouse-to-request travel in minutes. Part wait days should be an integer. Assignment cost should be a decimal value rounded to exactly two decimal places. Each row represents one assigned request, and unassigned requests must not appear in the file.

In your final response, state the total number of requests that were successfully assigned, the number of requests that could not be assigned, the sum of all travel time minutes across every assignment, and the sum of all part wait days across every assignment.
