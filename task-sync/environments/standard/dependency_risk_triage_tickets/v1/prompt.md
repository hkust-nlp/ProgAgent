Your organisation maintains a fleet of production services, each backed by open-source dependencies that may harbour known vulnerabilities. You have been asked to perform a full triage of every currently open dependency alert, determine which production services are actually exposed, and produce a prioritised set of remediation tickets so the responsible teams can begin patching within their contractual SLA windows.

Start by collecting every open alert from the dependency-scanning system, paging through the full result set so nothing is missed. For each open alert, retrieve its complete details — in particular the CVE identifier and the version in which the vulnerability was patched. You will also find a collection of production deployment manifests stored as individual JSON files; each manifest lists the dependencies a given service currently runs along with the exact installed version. A deployment is considered vulnerable when its installed version is strictly less than the patched version recorded in the alert. Version comparison follows semantic-versioning rules: compare major, then minor, then patch, all numerically.

Not every open alert warrants a new ticket. A plain-text exceptions file lists packages that security leadership has already reviewed and approved; alerts targeting any of those packages must be silently excluded. Separately, you must consult the remediation history for each alert to check whether an earlier ticket already covers the same alert-and-service combination. If a historical ticket for that pair carries a status of "in_progress" or "completed", do not create a duplicate.

Once you have identified every qualifying alert-and-service pair, enrich each with threat-intelligence data by querying for the CVE to obtain the exploit maturity rating, and look up service ownership to learn the owning team, the service tier, and the on-call email address. A YAML configuration file defines numeric weights for severity levels, exploit-maturity categories, and service tiers. Compute a priority score for each ticket as the product of the three corresponding weights — that is, the severity weight multiplied by the exploit-maturity weight multiplied by the service-tier weight. A second YAML file specifies SLA tiers; each tier has a minimum priority-score threshold, an SLA deadline in hours, and a label. Assign the first SLA tier whose minimum threshold the ticket's priority score meets or exceeds, scanning from the highest threshold downward.

Save the results as `prioritized_tickets.csv`. The file must contain exactly these columns in this order: `ticket_id`, `alert_id`, `cve_id`, `package_name`, `service_name`, `severity`, `exploit_maturity`, `service_tier`, `priority_score`, `sla_hours`, `sla_label`, `assigned_team`, `oncall_email`. Sort the rows by priority score in descending order; where two rows share the same score, break the tie by alert ID ascending and then by service name ascending. The ticket ID column uses the format `TKT-NNNN` where NNNN is a zero-padded four-digit sequence starting at 0001, assigned after sorting.

Conclude your response with a brief summary stating the total number of tickets created and the count in each SLA tier, formatted on separate lines as "Total tickets: N" followed by one line per tier in the form "P0-Critical: N", "P1-High: N", "P2-Medium: N", "P3-Low: N", including tiers with a count of zero.
