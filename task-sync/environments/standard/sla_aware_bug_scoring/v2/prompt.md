Your engineering organization conducts a weekly bug triage meeting where every newly reported bug must be scored, ranked, and assigned to a developer before the session begins. You have been asked to prepare the full triage queue this week. The inputs you need are spread across several sources: individual bug report files sitting in the current directory describe each new bug along with its severity, the feature it affects, and the customer who reported it. Developer availability for the coming week is captured in CSV schedule files also in the current directory, listing each developer's available hours, on-call status, PTO days, and current sprint load percentage. Three configuration files govern how scoring and assignment work: an SLA configuration file in YAML format defines response and resolution windows per contract tier along with a late-penalty rate; a JSON file specifies the weights and base scores used to compute the final priority number; and a YAML team-module mapping file describes which engineering team owns each product module together with rules about experience minimums for critical bugs and workload caps.

The priority score for each bug is a weighted sum of four components. The first component is a severity score, looked up from a table of severity-to-numeric-value mappings provided in the scoring configuration, then multiplied by the severity weight. The second component captures SLA urgency: you must retrieve the reporting customer's contract tier through the available tooling, map that tier to a numeric urgency score as specified in the scoring weights file, and multiply by the SLA urgency weight. The third component reflects the impact of the affected feature: retrieve the feature's telemetry data, normalize its daily active user count to a zero-to-ten scale relative to the highest daily active user count across all features in the system, then multiply that normalized value by one plus the feature's error rate times ten, and finally apply the feature impact weight. The fourth component accounts for historical fix complexity: pull the historical bug fix records for the affected feature, compute the average fix time in hours, normalize that average to a zero-to-ten scale relative to the largest average fix time observed across all features, subtract the result from ten so that features historically fixed quickly receive a higher urgency nudge, and multiply by the historical complexity weight. When the affected feature has no historical records, treat its average fix time as the largest average fix time observed across all features for the purpose of this component. Sum the four weighted components and round the result to two decimal places to obtain the priority score.

Once every bug has been scored, sort them in descending order of priority score. When two bugs share the same score, break the tie by sorting their bug identifiers in ascending lexicographic order. Assign a one-based integer rank to each entry in that sorted order.

For each bug you must also recommend a developer to handle the fix. Start by identifying the team responsible for the bug's module using the team-module mapping. From that team's roster, retrieved through the available tooling, filter out any developer whose ratio of active bugs to maximum concurrent bugs meets or exceeds the workload cap specified in the assignment rules. For critical-severity bugs, additionally exclude developers with fewer years of experience than the minimum stated in the rules. Exclude anyone whose schedule shows zero available hours or four or more PTO days this week. Among the remaining candidates score each one by computing a composite of their remaining workload capacity weighted at fifty, their years of experience weighted at three per year, their sprint headroom calculated as forty minus their sprint load percentage weighted at half a point per unit, and their available hours weighted at zero-point-two per hour. Select the developer with the highest composite score. If no eligible candidate exists on the target team, apply the same filtering and scoring across developers from all teams, omitting the sprint-headroom component in the fallback composite, and pick the best overall candidate. If still nobody qualifies, record the assignee as UNASSIGNED.

The estimated fix hours for a bug equal the average historical fix time for its affected feature, rounded to one decimal place. If no historical data exists for that feature, use the largest average fix time observed across all features instead.

Save the final ranked queue as `triage_queue.csv` with the following columns in this exact order: `bug_id`, `priority_score`, `priority_rank`, `recommended_assignee`, `sla_tier`, `estimated_fix_hours`. Every value must appear exactly as computed, with priority scores showing two decimal places and estimated fix hours showing one decimal place.

After writing the file, provide a concise summary that names the top three highest-priority bugs by their identifiers and states each one's priority score, recommended assignee, SLA tier, and estimated fix hours.
