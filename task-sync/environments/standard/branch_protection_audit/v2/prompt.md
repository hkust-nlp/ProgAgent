You are conducting a security compliance audit of branch protection rules across an organization's entire repository portfolio. The goal is to identify every instance where actual developer behavior violated the configured branch protection policies, classify each violation, apply any applicable exemptions, and produce a formal report the security team can act on.

Begin by reading the compliance policy configuration file, which defines four violation types together with their severity classifications and associated severity weights. The policy also specifies an escalation threshold: any repository whose cumulative weighted violation score meets or exceeds that threshold must be flagged for immediate escalation. Separately, load the exemptions file, which lists repositories that are fully exempt from all violation checks and individual users who are exempt from specific violation types. A reporting guidelines document describes the exact sorting and formatting rules for the output.

Merge event records are spread across several batch files in mixed formats. Collect every merge record; each one identifies the repository by name, the target branch, the pull request number, the merge commit SHA, the user who performed the merge, the timestamp, and whether the merge was an administrator override. You will also find a team ownership file mapping every repository to its owning team and a user roles file classifying each user.

For each repository that appears in the merge records, look up its numeric identifier using the available tools, then retrieve the branch protection rules configured for it. A protection rule may specify that pull request reviews are required along with a minimum approval count, that certain status checks must pass before merging, whether force pushes are disallowed, and whether administrators are subject to the same enforcement. A rule's branch pattern may be an exact branch name or a wildcard such as one ending with a slash and asterisk to cover all branches under that prefix.

Once you have the protection rules, go through every merge record whose target branch matches a protection rule pattern. For each such merge, retrieve the code review decisions for that pull request and count how many reviewers approved it; if the approval count falls below the minimum required, that merge is an insufficient-reviews violation. Next, retrieve the status check results for the merge commit SHA and compare them against the required status checks listed in the protection rule; if any required check has a failure status, that merge is a failed-status-checks violation. If the merge record indicates an administrator override and the matching rule has enforce-admins enabled, record an admin-override violation.

On top of merge-related checks, query every protected repository for forced push events. When a forced push lands on a branch matching a protection rule that disallows force pushes, record a force-push violation.

After assembling all raw violations, apply exemptions. Discard every violation for any repository listed as fully exempt. For individual user exemptions that are scoped to a specific violation type, discard only violations of that type committed by that user; other violation types by the same user remain. Attach each surviving violation's severity according to the compliance policy and look up the owning team from the team ownership data.

Save the final list as `violation_report.csv` with columns `repo_name`, `branch`, `violation_type`, `severity`, `offending_user`, `event_timestamp`, `description`, `owning_team`. Sort rows by severity weight descending so the most critical violations appear first, breaking ties by event timestamp ascending so the earliest event within the same severity comes first. Timestamps must be in ISO 8601 format without timezone, as in YYYY-MM-DDTHH:MM:SS.

Separately, produce `executive_summary.json` containing the following fields: `total_violations` as an integer, `by_severity` as an object mapping each of the four severity levels (critical, high, medium, low) to their respective counts, `by_type` as an object mapping each violation type (force_push, insufficient_reviews, failed_status_checks, admin_override) to its count, `top_offending_repos` as a list of up to five objects each with `repo_name` and `violation_count` sorted by count descending then name ascending, and `escalation_repos` as a sorted list of repository names whose cumulative weighted violation scores meet or exceed the escalation threshold from the compliance policy.

In your final response, state the total number of violations found and break them down by violation type and by severity level. Mention which repositories, if any, require escalation.
