You are working as the substitution engine for a grocery fulfillment center. A number of customer orders currently sitting in the pending queue contain items that are out of stock. Your job is to analyze every such order, determine which items cannot be fulfilled, and propose the best possible substitute for each missing item so that pickers on the warehouse floor receive a clear, ranked recommendation list they can act on immediately.

Begin by collecting the full set of orders that have at least one out-of-stock item. For every affected order, retrieve the order details and identify each item flagged as unavailable. You must also look up the customer who placed the order, because the substitution logic depends heavily on that customer's profile — in particular their price-sensitivity tier and loyalty score. Separately, each customer has a file of brand preferences and allergen avoidances that you will need to consult; these preferences are stored alongside other configuration data you can read from the file system, not from the tools directly.

The pool of eligible candidates for any out-of-stock item is restricted to other products that share the same top-level category as the original and that currently carry enough stock on hand to cover the requested quantity for that order line. Candidates outside the original's category, or whose available inventory falls below the ordered quantity, must not be considered.

Before scoring any candidate substitutes, read the substitution policy configuration carefully. It specifies the scoring weights assigned to five dimensions — category match, brand affinity, nutritional similarity, price compatibility, and inventory availability — as well as a bonus awarded when a candidate shares the exact subcategory of the original item. The policy also caps the number of substitutes that may be proposed per out-of-stock item (you must respect that cap). Additionally, the policy states that candidates whose allergens conflict with a customer's avoidance list must be excluded entirely, and it provides per-nutrient tolerance percentages that define how close a candidate's nutritional profile must be to the original in order to earn nutritional-similarity points.

Price sensitivity tiers are defined in a separate configuration file. Each tier specifies the maximum acceptable percentage increase in unit price relative to the original item. Any candidate whose price exceeds this ceiling must be discarded. The brand affinity matrix, also stored as a configuration file, gives a pairwise affinity score between every pair of brands represented in the catalog; use that score, scaled against the brand-affinity weight, to compute the brand component. If the candidate brand appears in the customer's preferred-brands list, add five bonus points to the brand component, capping the total brand contribution at the weight plus five.

For nutritional similarity, compare each of the seven nutritional fields (calories, protein, fat, carbs, fiber, sugar, sodium) between the original product and the candidate. For each field, if the candidate's value deviates from the original by no more than the tolerance percentage specified in the policy, award a proportional share of the nutritional-similarity weight (the weight divided equally among the seven fields). When the original value for a field is zero, treat any nonzero candidate value as exceeding tolerance.

Price compatibility scoring works as follows: if the candidate is cheaper than or equal to the original, award the full price-compatibility weight. Otherwise, reduce the score linearly in proportion to how much of the maximum allowable increase the candidate uses. Inventory availability scoring normalizes the candidate's current stock level against a reference of one hundred units, capping the ratio at one, and multiplies by the inventory-availability weight.

On top of these five scored dimensions, apply a quality bonus derived from each candidate's quality score found in the product specification files stored on disk. The bonus equals the candidate's quality score minus three, divided by two, then multiplied by five, so a quality score of five yields a bonus of five and a score of three yields zero.

Product specification files are organized in batches across multiple formats. Each record includes the product's dietary tags, allergen list, quality score, and sourcing origin. You must read all of these files to build a complete picture — some batches are JSON, some CSV, some YAML, and some plain text, and every product appears in exactly one batch.

There is one more critical data source: order-level notes left by customers. These notes indicate whether the customer allows substitution at all for that order and may contain a free-text preference note. If a customer has explicitly disallowed substitution for an order, you must skip that order entirely — no substitutions should be generated for it. The notes are spread across batch files in several formats, similar to the product specifications.

Once you have scored every eligible candidate for every out-of-stock item in every qualifying order, sort candidates in descending order of total score, breaking ties by ascending substitute product ID. Retain only the top candidates up to the per-item cap defined in the policy. Assign ranks starting from one.

Save the final output as `substitution_list.csv` with the following columns in this exact order: `order_id`, `original_product_id`, `rank`, `substitute_product_id`, `substitute_name`, `score`. Each score should be rounded to two decimal places. The file must contain one header row followed by one row per substitution entry, covering all qualifying orders and all their out-of-stock items.

When you report your results, state how many orders were processed, how many distinct out-of-stock items were handled, and how many total substitution entries were generated. Confirm that the output file has been written.
