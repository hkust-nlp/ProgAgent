You are an analyst at a renewable-energy regulatory body. Your mandate is to review every Renewable Energy Certificate transaction on file, cross-reference each one against generator accreditation records, metered generation data, market-timing rules, reference pricing, meter-validation findings, and buyer sustainability filings, and then produce a single consolidated anomaly report that flags every transaction exhibiting at least one irregularity.

Begin by reading the configuration files that govern the analysis. A JSON file describes the allowed trading hours (a start and end hour in UTC); any trade whose timestamp falls before that start hour or at or after that end hour constitutes an off-hours anomaly. A YAML file specifies numerical thresholds and severity classifications: an over-generation tolerance factor, a price-outlier standard-deviation multiplier, and a mapping from each anomaly type to a severity level (HIGH, MEDIUM, or LOW). A Markdown file lays out certification standards explaining when a generator's accreditation certificate should be considered invalid.

Retrieve all REC transactions through the available query interface, paginating as necessary. For every unique generator that appears among those transactions, retrieve its accreditation certificate. A transaction is an EXPIRED_CERT anomaly when the trade date falls after the certificate's expiry date or the certificate's status is anything other than "active."

Next, aggregate the total quantity of RECs sold per generator per vintage month. For each such combination, retrieve the corresponding meter reading. If the total sold quantity exceeds the metered total generation multiplied by the over-generation tolerance from the thresholds file, every transaction contributing to that combination is an OVER_GENERATION anomaly.

Separately, consult the meter-validation batch files (CSV format, each containing a generator identifier, a month, a validation status, an inspector identifier, and notes). Wherever the validation status is "FAIL" for a given generator and month, every transaction whose generator and vintage month match that entry is a FAILED_VALIDATION anomaly.

For pricing analysis, load the reference-price index files (JSON format, each record carrying a date, an energy type, a reference price, and a reference standard deviation). Compare each transaction's price per MWh against the reference price for the same date and energy type. When the absolute difference exceeds the price-outlier multiplier from the thresholds file times the reference standard deviation, flag that transaction as a PRICE_OUTLIER anomaly.

To detect double-counting, read the buyer sustainability-claims batch files (YAML format, each entry listing a buyer identifier and the REC serial numbers that buyer claims). If any serial number appears in the claims of more than one buyer, every transaction carrying that serial is a DOUBLE_COUNT anomaly.

Once all checks are complete, compile the results into a file called `anomaly_report.csv`. Each row must contain the columns `transaction_id`, `rec_serial`, `generator_id`, `buyer_id`, `trade_date`, `anomaly_type`, `severity`, and `details`, in that order. A single transaction may produce multiple rows if it triggers more than one anomaly type. Sort the entire report first by severity in descending priority (HIGH before MEDIUM before LOW), then by transaction_id in ascending lexicographic order within the same severity tier.

The severity for each anomaly type must match the mapping in the thresholds configuration. The details field should be a brief human-readable string noting the specific values that caused the flag, such as the certificate status and expiry date for an expired-cert finding or the sold-versus-metered quantities for an over-generation finding.

After writing the report, state in your final response how many total anomaly records the report contains, how many unique transactions are flagged, and provide a per-anomaly-type count.
