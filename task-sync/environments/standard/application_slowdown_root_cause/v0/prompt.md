Your organization is experiencing intermittent application slowdowns across multiple services, and the operations team needs a comprehensive root cause analysis that draws from every available data source. The goal is to identify which network devices are at the heart of these issues, determine why each one is failing, and produce a prioritized remediation plan backed by correlated evidence.

Begin by reviewing the configuration files in your working directory. A YAML file describes how different SNMP trap severities translate into numerical weights, and another YAML file lays out the full priority scoring formula along with root cause classification rules and their recommended remediation actions. A JSON file defines all network segments, including each segment's criticality level. Another JSON file establishes SLA tiers for each application, specifying response time thresholds and impact factors. Finally, a Markdown document explains the rules for correlating change management tickets with device issues, including tie-breaking logic when multiple tickets exist.

A device is considered "problematic" if it has at least one SNMP trap with severity of critical or major. For every such device, you must compute a severity score by summing the severity weights of all traps on that device, regardless of their individual severity level. You will also need to determine which network segment the device belongs to and look up that segment's criticality weight from the priority formula configuration.

To assess SLA impact, identify which applications have NetFlow sessions traversing each problematic device, then check whether any of those applications have APM traces with response times exceeding the application's tier-specific threshold. The maximum SLA impact factor among all breaching applications on a device becomes that device's SLA factor. If no application traversing the device breaches its SLA, use a factor of one.

For change correlation, look at all change management tickets associated with each problematic device. Follow the correlation rules described in the Markdown configuration to select the single most relevant ticket and its associated bonus value. If no qualifying ticket exists, record the correlated ticket as "NONE" and use a bonus of zero.

The final priority score for each device is computed as the product of the device severity score, the segment criticality weight, the maximum SLA impact factor, and the quantity one plus the change correlation bonus. Round the result to two decimal places.

Each problematic device must also be assigned a root cause classification. The classification rules are defined in the priority formula configuration and must be applied in the order listed, with the first matching rule taking precedence. Some rules require consulting the interface statistics CSV files in your working directory, which contain per-interface packet loss rates, error counts, and utilization measurements that are not available through any other channel. Specifically, the interface degradation and packet loss classifications depend on the packet loss rate of the specific interface named on the relevant trap (matched by both device id and interface name) compared against the thresholds specified in the rules.

Once all problematic devices have been scored, classified, and matched with their correlated tickets, produce a file called `remediation_list.csv` in your working directory containing one row per problematic device, sorted in descending order by priority score, breaking ties first alphabetically by segment name and then alphabetically by device hostname. The CSV must contain exactly these columns in this order: `rank`, `segment_name`, `device_hostname`, `root_cause`, `priority_score`, `affected_apps`, `correlated_ticket_id`, `evidence_summary`, `recommended_action`. The rank column should be a sequential integer starting at one. The affected_apps column should list all SLA-breaching applications on that device, separated by a comma and a space. The recommended action should come from the mapping defined in the priority formula configuration for the device's root cause classification. The evidence_summary column should contain a brief note of the form "Severity score X, segment Y (Z), SLA factor W, change bonus V" where X is the device severity score, Y is the segment name, Z is the segment criticality, W is the SLA factor, and V is the change bonus.

In your final response, provide a summary listing each device by rank, hostname, segment, root cause classification, priority score, affected applications, and correlated ticket ID, along with the total count of problematic devices identified.
