Your organization relies on a broad catalog of components sourced from suppliers around the world. Recent disruptions have highlighted the danger of depending on a single supplier for any given component. You have been asked to conduct a thorough single-source supplier risk assessment and produce a prioritized mitigation list covering every component that currently depends on exactly one supplier.

Begin by reviewing the configuration and policy documents available to you. A YAML configuration file named `risk_config.yaml` defines the numerical weights assigned to each risk factor and the threshold values that determine risk tier boundaries. A companion document named `scoring_policy.md` explains in prose how each risk factor is normalized, how the weighted composite score is calculated, and how recommended actions are determined from the tier and the alternate-supplier qualification status. Read both files carefully before proceeding, because every scoring decision you make must follow the formulas and lookup rules described there.

Supplier financial health data is stored across a set of CSV files whose names begin with `supplier_financials_part_` and end with `.csv`. Each file contains rows keyed by supplier identifier, with a column called `financial_health_score` representing the supplier's overall financial robustness on a zero-to-one-hundred scale. You will need to read all of these files to collect every supplier's score. Separately, supplier quality audit results appear in plain-text files whose names start with `quality_audits_part_` and end with `.txt`. Each relevant line in those files follows the pattern of a supplier identifier, a pipe-delimited quality score, and an audit date; parse every such line to extract the quality audit score for each supplier.

Information about whether alternate suppliers exist for each component is spread across JSON files named with the prefix `component_alternates_part_` and the `.json` extension. Each record in those files includes a component identifier, the number of known alternate suppliers, and a qualification status string. You will need this information later when assigning recommended actions. Additionally, component lead-time data resides in YAML files prefixed with `lead_times_part_` and ending in `.yaml`, containing each component's lead time in days; while these files round out your understanding of the supply chain, the core risk scoring formula relies on inventory coverage rather than raw lead time.

Once you have absorbed the workspace data, use the available tools to enumerate every component in the system. For each component, query the purchase order history filtered to that component and determine how many distinct suppliers have ever fulfilled orders for it. A component is classified as single-source when exactly one unique supplier appears across all of its purchase orders regardless of order status.

For every single-source component you identify, gather the following through tool calls: the supplier's detailed record including the country in which it operates, the geopolitical risk data for that country, and the current inventory level for the component which includes quantity on hand, daily usage rate, and a computed coverage-in-days figure. Combine these tool-derived values with the financial health score and quality audit score you already extracted from files.

Compute the composite risk score for each single-source component by applying the normalization rules and weighted sum described in the scoring policy document. Assign a risk tier to each entry using the tier thresholds from the configuration file. Determine the recommended action for each entry by cross-referencing its risk tier with the qualification status of its known alternate suppliers, following the action lookup table in the scoring policy.

Produce a file called `mitigation_list.csv` containing one row per single-source component, sorted by composite risk score in descending order with ties broken by component identifier in ascending lexicographic order. The file must include exactly these columns in this order: `rank`, `component_id`, `component_name`, `category`, `supplier_id`, `supplier_name`, `supplier_country`, `financial_health_score`, `geopolitical_risk_index`, `inventory_coverage_days`, `quality_audit_score`, `composite_risk_score`, `risk_tier`, `recommended_action`. The rank column should start at one and increment sequentially following the sorted order. Composite risk scores should be rounded to two decimal places.

In your final response, state the total number of single-source components you identified, provide a breakdown of how many fall into each risk tier (Critical, High, Medium, Low), and list the top five highest-risk components by their component identifiers, names, supplier names with countries, composite risk scores, and risk tiers.
