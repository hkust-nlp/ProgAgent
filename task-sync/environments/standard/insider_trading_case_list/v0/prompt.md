The compliance department needs your help building a prioritized investigation case list for potential insider trading activity. The goal is to cross-reference several data sources to identify employees whose trading behavior, data access patterns, and correlated market signals raise red flags worthy of further scrutiny.

You have access to tools that let you query the employee directory, trade pre-clearance logs, corporate event calendar, sensitive data access records, and unusual options volume alerts. Each of these tools returns paginated results, so you will need to iterate through all pages to obtain complete data. Separately, there are files available to you that contain broker trade confirmations, prior compliance investigation memos, employee portfolio holdings snapshots, and market data snapshots. There are also two configuration files you must consult: one is a YAML policy document that defines key parameters such as the blackout window length (how many days before a corporate event employee trades are restricted), the lookback period for flagging sensitive data access, the correlation window for matching options alerts to trades, tier thresholds and their recommended actions, the minimum score for including a case, and the multiplier applied when a repeat offender is identified. The other is a JSON file describing each risk flag, its point value, the output format specification, and the scoring methodology.

Your primary analysis works as follows. For every trade pre-clearance log, determine whether the trade was requested within the blackout window preceding any corporate event on the same ticker. The blackout window is measured as the number of calendar days between the trade request date and the event date: if the event date minus the request date falls between zero and the blackout window length (inclusive on both ends), the trade is considered a blackout violation. When a blackout violation is found, check whether the related corporate event has a sensitivity level of four or higher, which triggers an additional flag. For that same employee-ticker combination, look at the employee's sensitive data access records and determine whether any access occurred within the lookback period before the corporate event date (again, event date minus access date between zero and the lookback length inclusive). Also examine the options volume alerts for that ticker: if any alert date falls within the correlation window of the trade request date (the absolute difference in days is less than or equal to the window), that triggers yet another flag. Once the first matching event is found for a given trade, stop checking further events for that trade.

In parallel, you must examine the broker trade confirmations found across all the CSV files in your environment. Each broker confirmation row identifies an employee, a ticker, and an execution date. Compare these against the set of executed trades in the pre-clearance system. Specifically, build the set of all (employee ID, ticker, execution date) triples from pre-clearance logs that have a non-null execution date, and flag any broker confirmation whose triple does not appear in that set as an unreported trade.

Each distinct (employee ID, ticker) pair that has at least one triggered flag constitutes a potential case. After assembling all flags for a case, apply two additional flags if applicable: if the employee is designated as an officer in the employee directory, add the officer trade flag; if the employee's ID appears as a prior subject in any of the compliance memo text files, add the repeat offender flag. Subject lines in those memos follow the pattern where the employee ID appears immediately after a colon, before a space and parenthetical name.

To compute the risk score for a case, sum the point values of all triggered flags as specified in the scoring rules configuration. If the repeat offender flag is among those triggered, multiply the entire sum by the repeat offender multiplier from the policy file, then round the result to the nearest integer. Only cases whose final risk score meets or exceeds the minimum inclusion threshold should appear in the output.

Assign each qualifying case a risk tier based on the tier thresholds in the policy: check tiers in descending order of their minimum score, and the first tier whose minimum the case meets determines the tier and recommended action. Sort all qualifying cases by risk score in descending order, breaking ties by employee name in ascending alphabetical order. Then assign sequential case IDs in the format CASE-NNNN starting from 0001, where the numbering follows the final sorted order.

Save the result as `investigation_cases.csv` with exactly these columns in this order: `case_id`, `employee_id`, `employee_name`, `ticker`, `risk_score`, `risk_tier`, `flags`, `recommended_action`. The flags column must contain all triggered flags for that case joined by the pipe character, with individual flag names sorted alphabetically. Risk scores must be integers.

Once the file is written, provide a summary in your response that states the total number of cases generated, a breakdown of how many cases fall into each tier, and the details of the highest-scoring case including the employee name.
