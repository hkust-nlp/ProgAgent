A security incident has been escalated following automated alerts indicating potential data exfiltration from the corporate network. Your task is to conduct a thorough forensic analysis by correlating multiple data sources and produce a containment report identifying all compromised assets.

Your investigation must begin with the organizational incident response parameters, which define what constitutes off-hours activity, the minimum egress byte transfer threshold for flagging suspicious connections, the number of failed authentication attempts that warrant suspicion, and which file access actions are considered suspicious. These parameters are documented in a policy configuration file that you should consult before starting the analysis. Separately, a clearance matrix document maps each organizational role to the maximum data classification level that role is authorized to access. A data classification guide explains the five-tier classification hierarchy used across the organization, from least to most sensitive. A department risk scoring document assigns a numerical risk score to each department, which you will use for ordering your findings.

Threat intelligence is provided as a series of numbered feed reports. Each report contains indicators of compromise, including IP addresses tagged with threat categories and confidence levels. For this investigation, only IPv4 indicators with status marked as active, confidence of high or medium, and threat category of either C2 or exfiltration should be treated as confirmed malicious indicators. All other indicators should be disregarded. Once you have assembled the complete set of malicious IP addresses from all available feeds, you must cross-reference them against a list of known safe destinations maintained by the security operations team. Any IP appearing on that safe destinations list must be removed from your malicious indicator set, as these have been verified as legitimate organizational endpoints despite appearing in external threat feeds.

With the filtered malicious IP set established, examine all firewall egress log entries to identify connections where the destination IP matches a confirmed malicious indicator, the bytes transferred exceed the policy-defined threshold, and the connection occurred during off-hours as defined in the policy. Extract the distinct set of user identifiers associated with these flagged connections as your initial pool of suspected compromised accounts.

For each suspected user, review their authentication history and count the total number of failed authentication attempts on record. Only users whose total failed attempt count meets or exceeds the policy-defined threshold should be confirmed as compromised. Users falling below that threshold should be excluded from further analysis.

For each confirmed compromised user, examine their file access audit trail. Identify all access events where the action type matches one of the policy-defined suspicious actions and the access occurred during off-hours. For each such event, retrieve the metadata of the accessed file, including its data classification level. Exclude any access events involving files classified as PUBLIC, as these do not constitute a data breach regardless of the circumstances.

Determine the severity of each finding based on the file's classification level using the severity level definitions in the incident response policy. Additionally, consult the clearance matrix to determine whether each access was unauthorized by comparing the file's classification against the maximum classification allowed for the user's role as specified in the clearance matrix. Mark each finding as unauthorized if the file's classification strictly exceeds the user's role-based clearance level per the hierarchy defined in the classification guide.

Produce a file called `containment_report.csv` containing one row per suspicious file access event with the following columns in this exact order: `user_id`, `username`, `department`, `role`, `clearance_level`, `file_id`, `filename`, `classification`, `access_action`, `access_timestamp`, `endpoint_id`, `severity`, `unauthorized`. The unauthorized column should contain the string TRUE or FALSE. Sort the rows first by severity in descending order of criticality, meaning CRITICAL appears first, then HIGH, then MEDIUM, then LOW. Within the same severity level, sort by department risk score in descending numerical order. Within the same severity and department risk score, sort by user_id in ascending lexicographic order. Within the same severity, department risk score, and user_id, sort by file_id in ascending lexicographic order. If all four of those keys are identical, break ties by access_timestamp in ascending order.

Produce a file called `affected_assets.json` containing a JSON object with four keys. The key `compromised_users` should map to a sorted list of confirmed compromised user ID strings. The key `exfiltrated_files` should map to a sorted list of unique file ID strings drawn from all rows in the containment report. The key `affected_endpoints` should map to a sorted list of unique endpoint ID strings drawn from all rows in the containment report. The key `severity_breakdown` should map to an object with keys CRITICAL, HIGH, MEDIUM, and LOW, each mapping to the integer count of containment report rows at that severity level.

In your final response, include exactly these three summary lines. The first line should read COMPROMISED_USERS: followed by the confirmed compromised user IDs separated by a comma and a space, in sorted order. The second line should read TOTAL_EXFILTRATED_FILES: followed by the count of unique exfiltrated file IDs from the containment report. The third line should read SEVERITY_BREAKDOWN: followed by entries in the format CRITICAL:count, HIGH:count, MEDIUM:count, LOW:count with each pair separated by a comma and a space.
