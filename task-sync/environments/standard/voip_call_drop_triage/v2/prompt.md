Your organization has been experiencing intermittent VoIP call drops across multiple office locations, and the engineering team needs a comprehensive fault localization report to guide remediation. The relevant diagnostic data spans several sources: real-time packet loss metrics collected by network probes, SIP server error logs, endpoint firmware records, and wireless access point health assessments. Some of this information is available through the monitoring tools at your disposal, while additional context resides in data files you can read directly — configuration parameters, probe snapshots, AP health reports, firmware compatibility matrices, and severity classification guidelines. Solving this triage requires cross-referencing both tool-retrieved data and file-based data; neither alone is sufficient.

Begin by reading the threshold configuration file named `thresholds.yaml`, which defines numeric boundaries for packet loss, jitter, latency, MOS score, AP health, and SIP server load — these thresholds govern every classification decision you will make. Separately, read `firmware_compatibility.json` to learn which firmware versions are known-buggy, end-of-life, or associated with codec issues. Then read `severity_rules.md`, which explains in detail how to assign severity levels and attribute fault sources to endpoints. Together these three files define the decision logic you must follow precisely.

Once you have internalized those rules, begin gathering data. Use the available tools to list all SIP servers, then retrieve SIP error details for each server. List all network probes and pull aggregated packet loss metrics from every probe; these metrics include per-endpoint averages for packet loss percentage, jitter, latency, and MOS score. For every endpoint that appears in probe metrics, retrieve its detailed endpoint information to learn its firmware version, AP association, SIP server assignment, and location. Also fetch that endpoint's SIP error summary to learn its total error count and which error codes were recorded. For every unique access point referenced by those endpoints, retrieve the AP details including client health score.

You will also find probe snapshot CSV files and AP health report JSON files among the readable data files. The probe snapshots contain technician notes that flag endpoints under review; the AP health reports include channel utilization and co-channel interference data. Read these files and incorporate their context into your understanding, although the primary classification decisions are driven by the tool-retrieved metrics and the rules in the configuration files.

With all data in hand, classify every endpoint that exhibits at least one fault condition according to the severity rules. A fault is assigned one of four severity levels — CRITICAL, HIGH, MEDIUM, or LOW — and exactly one primary fault source — "network", "sip_server", "firmware", or "wireless" — following the precedence and tie-breaking rules in `severity_rules.md`. An endpoint that meets no fault condition should not appear in your report. When evaluating whether an endpoint's average packet loss exceeds a threshold, use the weighted average across all probes that measured that endpoint, weighted by sample count. Severity conditions are checked in order from CRITICAL down to MEDIUM; the first match wins. The LOW level is not expected to appear under current rules but exists as a fallback.

After classifying all faulty endpoints, produce a file named `fault_localization_report.csv` containing exactly these columns in this order: `endpoint_id`, `severity`, `fault_source`, `avg_packet_loss`, `avg_jitter`, `avg_mos`, `sip_error_count`, `firmware_version`, `ap_health_score`, `location`. Sort the rows first by severity in descending urgency (CRITICAL first, then HIGH, then MEDIUM, then LOW), and within the same severity level sort by endpoint_id in ascending alphabetical order. Numeric fields for avg_packet_loss, avg_jitter, and avg_mos should be rounded to two decimal places. The sip_error_count should be an integer. The ap_health_score should reflect the client health score of the AP to which the endpoint is connected.

In your final response, provide a concise summary of the triage findings. State the total number of faulty endpoints identified, break down how many fall into each severity level, and break down how many are attributed to each fault source category. Mention that the detailed report has been saved as `fault_localization_report.csv` and note that critical and high severity faults require immediate attention from the network engineering team.
