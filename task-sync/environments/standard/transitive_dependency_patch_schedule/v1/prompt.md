Your organization maintains a portfolio of production services whose software supply chains contain numerous indirect (transitive) dependencies. Recent audits have revealed that outdated transitive packages harbor unpatched vulnerabilities that go unnoticed because attention is traditionally focused on direct dependencies. Your job is to produce a comprehensive, prioritized patch schedule covering every high-severity vulnerability that resides in a transitive dependency, is actually deployed in production, and has a released fix.

Begin by examining the available software bill-of-materials documents, which enumerate every component in the dependency trees of the organization's services. Each entry in these documents indicates whether a package is pulled in directly or transitively, and if transitive, which parent package introduced it. Separately, vulnerability advisory feeds are provided as structured data that list CVE identifiers alongside the affected component and the severity classification. You should focus exclusively on vulnerabilities rated Critical or High. For every such CVE that targets a transitive component, retrieve the full vulnerability record through the available lookup capability to obtain the numeric CVSS score and, critically, the version of the component that resolves the issue. If no fix version exists for a given CVE, that entry must be excluded from the schedule entirely.

Once you have identified each CVE together with its affected transitive component, current version, and fix version, determine which production services are exposed. A transitive dependency is considered deployed to a service if the direct dependency it descends from is actively running in that service's production environment. You can query service-level deployment information through the provided tooling. Only CVEs whose affected component can be traced to at least one active production service belong in the final schedule.

Scoring each entry requires a prioritization policy and a service-criticality tier map, both of which are available as configuration files among the provided data. The priority score for a vulnerability is computed as the product of three factors: the CVSS score, the severity weight defined in the policy, and the highest service-criticality multiplier across all affected services for that CVE. Round the priority score to two decimal places. The patch deadline for each entry is the policy's reference date plus the number of grace-period days prescribed for that severity level.

Sort the completed schedule first by priority score from highest to lowest. Break ties by CVSS score descending, then by CVE identifier in ascending lexicographic order. Assign an integer rank starting from one.

Save the result as `patch_schedule.csv` containing exactly these columns in this order: `rank`, `cve_id`, `component_name`, `current_version`, `patched_version`, `severity`, `cvss_score`, `priority_score`, `affected_services`, `patch_deadline`. In the `affected_services` column, list every impacted service name separated by semicolons, with the names in alphabetical order within each cell. The `cvss_score` field should carry one decimal digit and `priority_score` two decimal digits.

In your final response, state the total number of entries in the schedule, the count of Critical entries versus High entries, and name the top three highest-priority items by CVE identifier and component name.
