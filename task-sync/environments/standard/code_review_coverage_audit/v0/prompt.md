You are conducting a comprehensive audit of code review practices across a portfolio of software repositories to determine the release readiness of every release currently awaiting review. Your data sources include structured configuration files that describe each repository's criticality classification and reviewer requirements, a review policy document that defines tier-based quality thresholds, a severity weighting reference for static analysis findings, and a set of queryable records covering repositories, releases, pull requests, review comments, static analysis violations, and historical defect escapes.

Begin by identifying every release that is in a pending review state. For each such release, determine the repository it belongs to, then look up that repository's criticality tier and minimum reviewer requirement from the configuration files. The configuration files are spread across multiple batches in various formats, so you must examine all of them to locate every repository's profile.

Four quality metrics govern the go or no-go decision for each pending release. The first is review coverage, defined as the fraction of pull requests within the release that received comments from a sufficient number of distinct reviewers. A reviewer is counted only if they are not the author of the pull request and have left at least one review comment on it. The threshold for how many unique reviewers qualify a pull request as adequately reviewed is the repository-specific minimum reviewer count found in the configuration files. Review coverage equals the number of adequately reviewed pull requests divided by the total number of pull requests in that release.

The second metric is comment density, computed as the total count of review comments across all pull requests in the release divided by the total number of lines changed, where lines changed equals lines added plus lines deleted across those pull requests.

The third metric is the weighted count of unresolved static analysis violations. For every pull request in the release, examine all static analysis violations. Only those that remain unresolved contribute to the total. Each unresolved violation's severity is mapped to a numeric weight using the severity weighting reference file, and the weighted sum across all unresolved violations in all pull requests of the release is the final figure.

The fourth metric is the historical defect escape rate for the repository. To compute this, look at all releases of the same repository that have already been released. Sum the total number of defect escapes across those past releases, and divide by the total number of pull requests across those same past releases. If the repository has no previously released releases, the defect escape rate is zero.

Once all four metrics are computed for a pending release, compare each against the corresponding threshold from the review policy configuration. The policy file organizes thresholds by criticality tier, specifying a minimum for review coverage, a minimum for comment density, a maximum for weighted unresolved violations, and a maximum for defect escape rate. A release earns a "GO" decision only when every metric satisfies its respective threshold. If any one metric fails, the release is classified as "NO-GO" and the names of the failing criteria must be recorded.

Save the complete results to a file named `audit_report.csv`, with one row per pending release sorted by release identifier in ascending order. The file must contain exactly these columns in this order: `release_id`, `repo_name`, `version`, `criticality_tier`, `review_coverage`, `comment_density`, `weighted_violations`, `defect_escape_rate`, `decision`, `failed_criteria`. Format review coverage, comment density, and defect escape rate as numbers rounded to four decimal places. Weighted violations must be an integer. The decision column should contain exactly "GO" or "NO-GO". The failed criteria column should list the metric names that failed their threshold checks, separated by semicolons using exactly these identifiers: "review_coverage", "comment_density", "weighted_violations", "defect_escape_rate". When all metrics pass, write the word "none" instead.

In your final response, include one line per pending release following the pattern "Release <id>: <decision>" where the identifier is the numeric release ID and the decision is GO or NO-GO, presented in ascending order by release identifier. Conclude with a summary line in the exact format "SUMMARY: X GO, Y NO-GO" where X and Y are the counts of each decision type.
