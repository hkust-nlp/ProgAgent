You are tasked with conducting a comprehensive anomaly investigation across a commercial vehicle fleet to identify potential fuel theft, unauthorized vehicle usage, and maintenance-period violations. The fleet operates out of several depots, each defined by a geographic center point and a geofence radius. Every fuel card transaction, GPS tracking event, and driver shift record is available for querying through the data tools at your disposal. Separately, a collection of files in your working directory contains the depot geofence definitions, anomaly detection thresholds, vehicle type specifications, scheduled maintenance windows, approved overtime records, fuel pump receipts, and historical incident logs. You will need to consult all of these sources to reach correct conclusions, as the information required to solve the task is distributed across both the queryable records and the files.

Your investigation must identify five categories of anomalies. The first category is off-geofence fueling, which applies whenever a fuel card transaction occurs at a location whose distance from every depot center exceeds that depot's geofence radius. The distance threshold that separates normal proximity from a flagged event is specified in the anomaly thresholds configuration file, as is the distance beyond which severity should be elevated. You will need to compute the great-circle distance between each transaction's coordinates and every depot's coordinates, using the depot data found in the geofence definitions file, and flag any transaction that falls outside all geofences.

The second category is overcapacity fueling. Each vehicle type has a defined fuel tank capacity listed in the vehicle type specifications file. When a fuel card transaction records a liter amount that exceeds a configurable percentage of the vehicle's tank capacity, it signals a suspicious fill. The percentage thresholds for flagging and for elevated severity are both found in the anomaly thresholds file. To perform this check you must look up each vehicle's type through the data tools and then cross-reference against the capacity listed in the specifications file.

The third category is maintenance-period movement. Scheduled maintenance windows are recorded in the maintenance schedule files. Any GPS event showing a vehicle traveling above a speed threshold during one of its scheduled maintenance windows constitutes an anomaly. The speed threshold and the elevated-severity speed cutoff are both defined in the anomaly thresholds file. You must read every maintenance schedule file, then query GPS events for the relevant vehicles and time ranges, and flag any event where the speed exceeds the threshold while the timestamp falls within the maintenance window.

The fourth category is after-hours ignition. A GPS event with the ignition turned on that falls outside the driver's scheduled shift hours for that day is suspicious. Shift schedules are available through the data tools. However, some after-hours activity is legitimate because it has been pre-approved as overtime. Approved overtime records are stored in the fleet daily report files and specify the vehicle, the date, and the hour range during which extended operation was authorized. An ignition event that falls within an approved overtime window should not be flagged. The severity thresholds file specifies an hour range during which after-hours ignition is considered especially severe. Only events occurring on days when the vehicle actually has a scheduled shift should be evaluated; days with no shift record for a vehicle are not subject to this check.

The fifth category is fuel receipt mismatch. Fuel pump receipts are recorded in the receipt batch files and contain a pump amount for each transaction, identified by transaction number. When the absolute difference between the pump-recorded amount and the card-recorded amount for the same transaction exceeds a liter threshold specified in the anomaly thresholds file, the discrepancy should be flagged. An elevated severity applies when the difference exceeds a higher liter cutoff, also defined in that file.

Once you have identified all anomalies across every category, you must also adjust severity levels based on historical incidents. The incident history files list vehicles that have prior records of suspicious activity. If the anomaly thresholds configuration enables the prior-incident severity upgrade, then any anomaly involving a vehicle with a prior incident should have its severity raised to HIGH regardless of the base severity determination. Anomalies for vehicles without prior incidents retain their base severity.

Save your final anomaly report as `anomaly_report.csv` in your working directory. The file must contain columns `incident_id`, `vehicle_id`, `plate_number`, `anomaly_type`, `reference_id`, `timestamp`, `severity`, and `details`, in exactly that order. The `anomaly_type` values must be one of `off_geofence_fueling`, `overcapacity_fueling`, `maintenance_movement`, `after_hours_ignition`, or `fuel_receipt_mismatch`. The `reference_id` should be the unique identifier of the underlying record as returned by the data tools, which is the transaction identifier for fuel-related anomalies and the event identifier for GPS-related anomalies. Severity must be either `HIGH` or `MEDIUM`. Rows must be sorted by severity with all `HIGH` entries before `MEDIUM` entries, and within the same severity level, by timestamp in ascending order. The `incident_id` column should contain sequential integers starting from one, assigned after sorting.

In your final response, state the total number of anomalies found, provide a count broken down by each anomaly type, and provide a count broken down by severity level. Also list any vehicles that appear in multiple anomalies.
