You are a release engineer responsible for evaluating all currently active canary deployments across the organization's microservice fleet. Your objective is to analyze each service undergoing canary release, score it across multiple performance dimensions, and deliver a final promotion, rollback, or hold recommendation for every service along with an aggregate release decision.

Begin by identifying every service currently deployed in canary status. For each such service, you will need to determine its tier classification, which governs the strictness of the evaluation thresholds applied to it. Consult the available configuration documents to understand the tier-specific limits for latency degradation, error rates, synthetic test success, and feature flag coverage, as well as the scoring weights and decision threshold boundaries that govern the promote-or-rollback determination.

The first scoring dimension is latency degradation. For each canary service, retrieve its recent latency measurements from the canary environment, specifically the p50 latency readings, and compute the average. Compare this average against the historical baseline latency recorded in the baseline data files. The degradation percentage is calculated as the difference between the canary average and the baseline, divided by the baseline, multiplied by one hundred. If this percentage falls at or below the tier's maximum allowed degradation, the latency score is one. If it reaches or exceeds double the tier's allowed maximum, the score is zero. Between these bounds, the score decreases linearly from one to zero. The result should be clamped to the range zero through one.

The second dimension concerns the error rate observed in the canary environment. Retrieve the error rate metric readings for each canary service and compute the average. If the average error rate is at or below the tier's maximum allowable error rate, the score is one. If it reaches or exceeds double that threshold, the score is zero. In between, it decreases linearly. Clamp to zero through one.

The third dimension is the synthetic transaction success rate. For each canary service, count the number of synthetic transactions in the canary environment that completed successfully and divide by the total number of canary-environment synthetic transactions. If the resulting rate meets or exceeds the tier's minimum required success rate, the score is one. If it falls to the minimum minus zero point one or below, the score is zero. In between, the score increases linearly from zero to one. Clamp to zero through one.

The fourth dimension evaluates feature flag rollout coverage. For each canary service, retrieve the current rollout percentage of every feature flag from the deployment system and compare each against the corresponding target rollout percentage recorded in the rollout target configuration files. Compute the ratio of actual to target for each flag and take the arithmetic mean across all flags belonging to that service that have a recorded target. If the average coverage ratio meets or exceeds the tier's minimum required flag coverage, the score is one. Otherwise, the score equals the ratio of the average coverage to the tier's minimum, clamped to zero through one.

Once the four component scores have been determined for a service, combine them into a single weighted score by multiplying each component by its respective weight as specified in the canary policy configuration and summing the products.

Before applying the score-based decision, two override conditions must be checked. First, examine the error logs from the canary environment for that service: if any log entry carries a severity of critical, the service must be assigned an automatic rollback decision regardless of its weighted score. Second, consult the deployment notes files: if a service is marked with a manual rollback override set to true, it must likewise receive an automatic rollback decision irrespective of scoring.

For services not subject to either override, the weighted score determines the outcome. A score at or above the promotion threshold yields a promote decision. A score strictly below the rollback threshold yields a rollback decision. Scores falling between these two thresholds result in a hold decision.

After individual service decisions have been made, derive the overall release decision as follows: if any service classified under the critical tier has been assigned a rollback decision, the overall decision is rollback. Otherwise, if every canary service received a promote decision, the overall decision is promote. In all remaining cases, the overall decision is hold.

Produce a file named `decision_report.csv` containing one row per canary service, sorted in ascending order by service identifier. The file must contain the following columns in this exact order: `service_id`, `service_name`, `tier`, `latency_degradation_pct`, `latency_score`, `error_rate`, `error_score`, `synthetic_success_rate`, `synthetic_score`, `flag_coverage`, `flag_score`, `weighted_score`, `has_critical_errors`, `has_manual_override`, `decision`. All floating-point values must be rounded to four decimal places. The `has_critical_errors` and `has_manual_override` columns should contain `true` or `false` in lowercase. The `decision` column should contain one of `PROMOTE`, `ROLLBACK`, or `HOLD`.

Separately, produce a file named `overall_summary.json` structured with keys `overall_decision` (one of `PROMOTE`, `ROLLBACK`, or `HOLD`), `total_canary_services` (integer count), `promote_count`, `rollback_count`, `hold_count` (each an integer), and `rollback_services` (a list of service names that received the rollback decision, sorted alphabetically).

In your final response, state the overall release decision, report the total number of canary services evaluated and how many fell into each decision category, and list by name every service that was assigned a rollback decision.
