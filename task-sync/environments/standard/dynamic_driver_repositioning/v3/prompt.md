You are acting as the dispatch coordinator for a ride-hailing platform during a busy afternoon period. Your objective is to produce two deliverables: an optimized dispatch priority list that pairs every assignable pending ride request with the most suitable available driver, and a repositioning plan that redirects idle drivers from oversupplied zones toward zones forecasting unmet demand.

Begin by collecting every ride request that is still waiting for assignment. Each request carries a pickup zone, a dropoff zone, a wait-tolerance window expressed in minutes, a ride type (standard, premium, or shared), and a passenger rating. You will also need the full roster of drivers whose status is currently available, including each driver's present zone, vehicle type, and rating. A configuration file in YAML format describes the dispatch policy: it specifies weighting coefficients for four scoring dimensions (demand, urgency, zone priority, and passenger rating), normalization parameters including a maximum wait-tolerance cap and the current operational hour, threshold values for the oversupply ratio and road-closure penalty factor, a same-zone base pickup time, a default travel-time estimate for zone pairs lacking direct data, and the decimal-place precision to use when rounding priority scores and travel times.

To compute the priority score for each pending request, you must combine information from multiple sources. First, retrieve the historical average-request count for the request's pickup zone at the operational hour indicated in the dispatch policy. Then consult the zone demand adjustment reports among your files; these Markdown documents contain a table listing every zone alongside any active event and its corresponding surge factor. Multiply the historical baseline by the surge factor to obtain the adjusted demand for that zone. Normalize this adjusted demand by dividing by the maximum adjusted demand observed across all pending requests' pickup zones. Second, derive an urgency component: subtract the request's wait tolerance from the maximum wait-tolerance cap defined in the policy, then divide by that cap, clamping the result between zero and one. Third, look up the zone's priority multiplier from the JSON zone-categories file, and normalize it by dividing by the largest multiplier in that file. Fourth, normalize the passenger's rating by dividing by five. The final priority score equals the demand weight times the normalized demand, plus the urgency weight times the normalized urgency, plus the zone-priority weight times the normalized zone multiplier, plus the passenger-rating weight times the normalized rating, rounded to the number of decimal places specified in the policy.

Sort all pending requests by priority score from highest to lowest; break ties by request identifier in ascending alphabetical order. Then, proceeding through the sorted list, assign each request to the best eligible driver. A driver is eligible if that driver has not already been assigned to another request during this process, is not flagged for overtime in the shift-log CSV files found among your data, operates a vehicle type permitted for the request's ride type according to the vehicle-rules YAML file, and meets the minimum driver-rating threshold for that ride type as stated in the same file. For each eligible candidate, calculate the estimated pickup time: if the driver is in the same zone as the pickup, use the same-zone base time from the policy; otherwise retrieve the current travel time between those zones, and if no data exists fall back to the default travel-time estimate. Additionally, check the traffic bulletins in your text files for road closures; if a route between the driver's zone and the pickup zone is listed as closed, multiply the travel time by the closure penalty factor from the policy. Round the resulting time to the precision specified in the policy. Choose the driver with the shortest estimated pickup time; if two drivers tie, prefer the one with the higher rating, and if still tied, prefer the one whose identifier comes first alphabetically.

After all possible assignments are made, turn to repositioning. Consider every available driver who was neither assigned to a request nor flagged for overtime. For each such driver, compute a supply-to-demand ratio for their current zone: the numerator is the count of remaining eligible drivers in that zone, and the denominator is the predicted request count for that zone taken from the demand-forecast JSON files among your data (treat any zone with zero or missing forecast as having a demand of one). If this ratio exceeds the oversupply threshold in the policy, identify a target zone to which the driver should relocate. The target is the zone with the greatest positive deficit, where deficit equals the forecast demand minus the current supply of remaining eligible drivers; break ties by choosing the zone whose identifier comes first alphabetically. Calculate the estimated travel time to the target zone using the same traffic lookup and closure-penalty logic described above. After repositioning a driver, update the supply counts for both the source and target zones before evaluating the next driver. Process drivers in ascending order of their identifier.

Save the dispatch priority list as `dispatch_priority.csv` with columns `request_id`, `assigned_driver_id`, `priority_score`, `estimated_pickup_min`, and `dispatch_order`, where dispatch order is a sequential integer starting at one reflecting position in the priority-sorted, successfully assigned list. Save the repositioning instructions as `repositioning_plan.csv` with columns `driver_id`, `current_zone`, `target_zone`, `reason`, and `estimated_travel_min`. The reason field should read "Oversupplied zone X (ratio Y) to high-demand zone Z" where X is the driver's current zone, Y is the supply ratio rounded to one decimal, and Z is the target zone.

Conclude your response with a summary line in this exact format: SUMMARY: {pending_count} pending, {dispatched_count} dispatched, {avg_pickup_time} avg pickup min, {repositioned_count} repositioned, where pending_count is the total number of pending requests found, dispatched_count is how many were successfully assigned, avg_pickup_time is the mean estimated pickup time across dispatched requests rounded to one decimal place, and repositioned_count is the number of drivers given repositioning instructions.
